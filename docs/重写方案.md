# 重写方案（PSDTO3D NG）

目标：做一个**原生 64 位、跨平台、工程文件可移植、崩溃可诊断**的光栅立体图（lenticular）生成器，
在不牺牲画质的前提下接管现有两套老程序的工作，并能直接读取老工程。

---

## 1. 先把老程序的"事实"固定下来

重写的难点不在界面，而在**算法等价**。老程序已经用二进制把我们需要的口径暴露清楚了：

| 事实 | 证据 | 对新版的约束 |
|---|---|---|
| 工程 = PSD + 每层 angle/group/scale + 每层 offset + 手绘曲线 + 镜头/输出参数 | `.tw3d2` 文本格式（12/12 逐字节回写成功） | 新工程格式必须能无损表达这些字段（见 `schema/project-v1.json`） |
| 光栅 LPI、输出 DPI、视图数(Angles)、景深 | 行 2 / 行 8 / UI `3DSets` | 校验：`views>=1`、`lpi>0`、`dpi>0` |
| 交错索引 = `Round(f(层, 视图, LPI/DPI))` | `0x509F73`–`0x50A014` 的 FP 序列 | 需要与老的取整规则一致（含 Delphi 的银行家舍入 `Round`） |
| 输出 = 多通道 TIFF（CMYK/RGB/灰度） | `cmyktiff2.dll!bmptotiff / mergtotiff` | 用 libtiff 系实现，保持 CMYK 与通道顺序 |
| 图层必须"普通层"、不能有背景层 | `All layers must be simple layer…` | 导入时明确报错并给出修复建议，而不是继续跑 |
| 输出路径固定 `C:\ok3dtemp\`、PSD 绝对路径、加密狗 | 字符串与启动闸门 | 全部去掉：临时目录可配、路径相对化、无锁 |

## 2. 技术选型

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| **C# / .NET 8 + Avalonia** | 原生 64 位、单文件发布、UI 生产力高、跨平台、生态好（ImageSharp/SkiaSharp、BitMiracle.LibTiff.NET） | 大图重算需 SIMD 优化 | **推荐** |
| C++ / Qt6 | 极致性能与内存控制 | 开发慢、部署复杂、团队门槛高 | 核心算法可用 C++ 写动态库给 C# 调 |
| Rust + egui/tauri | 内存安全、性能好 | 图像/PSD 生态弱于 C#/.NET | 备选 |

推荐分层：

```
PSDTO3D.NG.sln
├─ Core        算法：图层模型、交错引擎、视图生成、几何/曲线
├─ Psd         PSD 读取：图层/组/蒙版/通道、RGB/CMYK/灰度、8/16bit
├─ Tiff        TIFF 写出：多通道、LZW/Deflate、CMYK、ICC
├─ Project     新 JSON 工程 + 老 .tw3d2 导入
├─ Cli         批处理 / 自动化（服务器端不用开界面）
└─ App         Avalonia 界面
```

关键库：`BitMiracle.LibTiff.NET`（TIFF，BSD）、`SkiaSharp`（缩放/合成、SIMD）、
`SixLabors.ImageSharp`（通用处理）、PSD 解析优先自研（格式公开，避免 GPL 依赖）。

## 3. 新工程格式（v1）

见 `schema/project-v1.json`。要点：

* **相对路径 + PSD 摘要**：`source.psd` 相对本文件，`source.sha256` 校验配对；
  配错 PSD 时直接报"工程与 PSD 不匹配（图层 29 vs 12）"，而不是崩在 `0x50A001`。
* **显式单位**：`lens.lpi`、`output.dpi`、`output.width/height`、`layers[].angle/scale`。
* **曲线段保留为点数组**，老工程可无损迁移。
* 可读、可 diff、可版本控制（老 `.tw3d2` 也能 diff，但字段名全靠猜）。

迁移已验证：`tools/tw3d2_to_json.py` 把 `kelex.tw3d2`（29 层 / 196 条曲线）转成 JSON，
图层、曲线、镜头参数、PSD 摘要全部就位。

## 4. 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| **M0 影子工具**（1–2 周） | `tw3d2 → JSON` 导入、工程校验 CLI、PSD 头解析 | 现有 12 个样本全部转换成功；`check --psd` 能抓出 2022 包里的坏样本 |
| **M1 算法等价**（3–4 周） | 交错引擎 + TIFF 输出，先做 RGB/8bit | 对 `3danimation`、`flip3x` 等样本，输出 TIFF 与老程序**逐像素一致**（PSNR=∞ / 差值为 0） |
| **M2 界面**（4–6 周） | Avalonia：导入 PSD、图层表、参数面板、预览 | 常用流程 5 分钟内跑通；无崩溃；错误可读 |
| **M3 生产化**（2–3 周） | 批处理 CLI、日志、断点、超大图分块 | 4GB+ PSD 可用（原生 64 位）；崩溃有堆栈与输入文件引用 |
| **M4 增强** | CMYK/16bit、ICC、GIF/MP4 预览、脚本接口 | 与老程序 CMYK 输出一致；客户可脚本化 |

## 5. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 交错取整规则与老程序差 1 像素 | 输出不一致，客户不认 | M1 用"逐像素一致"作硬门槛；先用老程序输出作为黄金样本 |
| PSD 变体多（16bit、CMYK、图层蒙版、智能对象） | 导入失败 | 先支持 8bit RGB/CMYK/灰度，其余明确报"不支持"，不猜 |
| 大图内存（10k DPI 输出） | OOM | 原生 64 位 + 分块（band）处理，落盘流式写 TIFF |
| 客户已有大量 `.tw3d2` 资产 | 迁移成本 | M0 的导入器 + 批量转换脚本；保留"回写 tw3d2"能力 |
| 颜色管理 | 印刷偏色 | 输出携带 ICC；CMYK 走 libtiff 的 ink 设置 |

## 6. 与老程序的并存策略

1. 新版先做**只读兼容**：能打开老工程、能产出同样的 TIFF；老程序继续干活。
2. 交接期用 `tools/` 里的体检脚本保证老工程数据是干净的（PSD 配对、图层数、Angles）。
3. 新版稳定后再停用老程序；`psdto3d2022绿色版` / `psdto3d10.1绿色版` 作为回归测试的"黄金实现"保留。

## 7. 现在就能开工的第一步

```powershell
# 1) 把全部老工程转成新格式，作为回归语料
python tools\tw3d2_to_json.py "psdto3d10.1绿色版\sample\kelex.tw3d2"

# 2) 用老程序对同一工程出图，存成黄金样本
# 3) M1 的交错引擎拿黄金样本做逐像素比对
```

工程骨架按第 2 节建好后，`Core` 只需要三个输入：PSD 图层位图、每层参数、镜头/输出参数；
其余全部是 I/O 与界面。**先用 CLI 跑通、再上界面**，是这个项目最省时间的顺序。
