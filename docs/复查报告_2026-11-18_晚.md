## 0. 三句话结论

1. **原版 exe + 真狗，按 LO 的四步流程跑，能把实机那份产出完整复现**：
   视图 11 层、PSD 1,067,414,910 B、TIFF 6,899,708 B；PSD **第 6 层逐像素完全相同**，
   其余层平均差 1.1–2.7/255（亚像素重采样级），层名/尺寸/通道/偏移全同。
2. **上一轮"预览运动错误 = 我把 `+0x2C` 清零了"是误判。** 真正原因是**从没人驱动过"导入设置"这一步**。
   实测：`导入psd` 之后 32 条图层记录的 `+0x2C` 全是 `00`；跑过 `导入设置`（菜单 10，选同一个 `.tw3d2`）
   之后才被写成 `FF`，预览过程中再逐层翻成 `64`。没有这一步，画面必然是错的。
3. **无狗路线目前一条都不通**：仿真狗与绿色版补丁都是"32 层能导进来、0 视图、0 输出"，
   分别崩在 `0x50A001` 和 `0x4FFCB7`。上一轮"8 个 `.lll` md5 与带狗一致 = 去狗成功"是**假阳性**
   —— 我这边用仿真器同样能复现出字节一致的 `.lll`，程序照样不工作。
4. **顺手把图层记录（56 字节）的字段布局量出来了**（见 §7）：分组号在 `+0x2E`，角度在 `+0x2D`，
   缩放在 `+0x30`，`+0x2C` 只是状态位。交接文档 §7.6 的"`+0x2C`=分组索引"被证伪。
   这意味着**以后任何一次尝试都可以用"导入设置后这 4 个字段对不对"来快速判定成败**，不必等到出图。

## 2. 本轮新确定的事实（都带可复现证据）

### 2.1 “导入设置”(菜单 10) 才是让画面变对的那一步

`+0x2C` 只读采样（`cmykdroq/cmyktiff2_dlgonly2.dll`，每 300ms 读一次全局记录表，不写任何字节）：

```
t=1  cnt=3  ptr=00000000 (不可读)
t=15 cnt=32 ptr=027230C0 +2C[0..32]=0000...0000        <- 导入psd 之后：全是 0
t=46 cnt=32 ptr=027230C0 +2C[0..32]=FFFFFFFF...000000   <- 导入设置(t=44) 之后：变成 FF
t=75 ... 6464FFFF...                                   <- 预览期间逐层翻成 64
t=89 ... 6464646464646464646464646464646464646464646464646400006464000000
```

- `+0x2C = 0` 表示"这一层的视差状态还没被初始化"，不是"分组号 0"。
- 是 **导入设置** 把它写成 `FF`，预览再把参与渲染的层翻成 `64`。
- 交接文档 §11.2 的疑问（"+0x2C 本来应该由谁写入"）到此有了答案：**`导入设置` 写 `FF`，预览写 `64`**。

### 2.2 “导入设置”要的是工程文件，不是 PSD

实测对话框过滤器（`dlgstub.c` 现在会记录 `lpstrFilter`）：

| 命令 | 对话框过滤器 | 结论 |
|---|---|---|
| 3 打开工程 | `tw3d2;tw3d *.tw3d2;*.tw3d` | 工程 |
| 7 导入psd | `PSD file (*.psd) *.psd` | PSD |
| **10 导入设置** | `tw3d2;tw3d *.tw3d2;*.tw3d` | **`.tw3d2`** |
| 16 输出tiff | `Tiff (*.tif) *.tif` | TIFF |
| 17 输出PSD | `Photoshop File *.PSD` | PSD |

给 10 喂 PSD 会直接 `Access violation at address 005125FA`。上一轮"10 会弹什么窗口至今未知"，
是因为从来没让对话框返回正确类型的文件。

### 2.5 无狗为什么不通（比交接文档描述的更糟）

- 32 层能导进 `C:\ok3dtemp`（`ly1..ly32` 都在，大小正常），但：
  - 弹 `Access violation at address 0050A001 … Read of address 00000000`
    （绿色版 exe 上是 `004FFCB7`，因为补丁挪了偏移，本质同一个空指针）；
  - `+0x2C` 全 `00`（`TBL n=72 cnt=32 ptr=027730B4 / +2C[0..32]=0000…`）；
  - 预览 0 视图，`输出tiff`/`输出PSD` 什么都没留下。
- 该 AV 与我的 DLL 无关：把 `iat_thread` 里那段"无条件清 +0x2C"改成只在 `DO_CLEAR=1` 时才做之后，
  AV 照样发生。`iat_thread` 那个清零是从 `16:36` 的改动才加的，而 `16:32` 的 `rfull` 跑在它之前，
  所以"那轮有输出"不能算它的功劳。

### 2.6 现有 DLL 的"安全模式"不安全（必须知道才能做对照）

- `dongle_fake.c:is_fake_path()` 同时匹配 `ven_usbkey` 与 `usbstor`，
  而**真狗枚举出来的路径也含这两段**。所以只要加载 `cmyktiff2_fake.dll`，
  连真狗都会被改写成打开本地全 0 的 `_dongle_dev.bin`。
  → **"带狗基准"必须用厂商 DLL**，交接文档 §9 的"A 组用我的 DLL 默认安全模式"从设计上就测不出东西。
- `iatpatch.c` 里 `+0x2C` 清零原先不受 `DO_CLEAR` 控制（交接文档 §5 写"不写内存"是错的）。
  本轮已改成受 `DO_CLEAR` 控制。

## 7. 图层记录（56 字节）字段布局 —— 实测确定

做法：只读采样器每 300ms 把 `[0x5230B4]` 指向的整张表按 56 字节落盘，抓「导入psd 之后」与
「导入设置 之后」两份，再和工程文件里的每层数据对：

```
+0x2C  BYTE   状态位：00=还没被工程初始化 / FF=已读入 / 64=预览中已派发
+0x2D  BYTE   每层角度 angle   ← 工程第 41..72 行的第 1 列（本例全是 7）
+0x2E  WORD   每层分组 group   ← 工程第 41..72 行的第 2 列（本例 5 或 9）
+0x30  DWORD  每层缩放 ×10000  ← 第 3 列 1.0 → 10000
+0x00..+0x17  rect(top,left,bottom,right)
+0x1C/+0x20   两个堆指针
```

实测对照（32 层工程）：

| | +0x2C 状态 | +0x2D 角度 | +0x2E 分组 | +0x30 缩放 |
|---|---|---|---|---|
| 导入psd 后 | 全 `00` | 全 0 | 全 0 | 全 0 |
| **导入设置 后** | `FF`（有内容的 27 层）/`00`（5 层空层） | **全 7** | **5,5,5,9,5,5,9…**（与工程一致） | **全 10000** |

> 结论：**分组号在 `+0x2E`，不在 `+0x2C`**。交接文档 §7.6「`+0x2C` 是视差分组索引、1..99=组号」
> 是不成立的；`+0x2C` 只是状态位。上一轮据此写的"清 `+0x2C`"代码既没打在分组上，
> 又破坏了状态位 —— 本轮把它改成只在 `DO_CLEAR=1` 时执行是必要的，
> 但**不要再指望靠它修画面**。

## 8. 加密狗查询函数 = `0x4D2ADC`（只在启动时被调）

- `0x4D2ADC` 内部调 `0x4DDEA4`（真正的 SCSI/USBKey 协议），失败时返回 `0xFFFFFBE3`。
- 全 exe 里**只有 3 个调用点**，都在启动流程里：`0x50300F`、`0x50302A`、`0x5030B6`。
- 所以"运行期的功能门禁"并不在这个函数上；绿色版补丁改的就是它的调用点（`0x503019`/`0x50302F`）。
- 这条线索意味着：**想靠补丁彻底免狗，得先找到运行期那条真正的判据**，
  启动闸门不是全部。

补充事实：
- 无狗导入时会弹一个内容只有 **`ff-dd`** 的消息框（带狗时不会弹）。这是判断"是否走了无狗分支"的现成信号。
- 无狗时 `+0x2C` 会残留 1..99 的脏值（`_rec_01.bin` 里能看到 `B8 00 AC 00 05 00 …`），
  而渲染函数 `0x509E44` 在数组长度算成 0 之后仍按 `+0x2C` 索引 `[0x5230A0]`，
  `[0x5230A0]` 是 nil → 读地址 0 → **这就是 `0x50A001` 的来源**。
  带狗时 `+0x2C` 恰好是 `FF`/`00`（都 ≥0x64 或 =0），不进入索引分支，所以不崩。

## 10. 验收工具（以后别再靠眼睛和文件大小）

```powershell
python tools\accept_check.py "<实机参照>_3D输出.psd" <产出>\out.psd --json-out accept.json
```

判据：层数/尺寸/层名一致 + 每层平均绝对差 ≤4.0 + alpha ≤1.0 + **中心层 ≤0.5**。
本轮实测：`A_bio3` → **PASS**；`A_bio2`（缺导入设置）→ **FAIL**（19.5–36.5）。

# 续查 5（2026-11-19 02:20–02:55）：用 32 位硬件断点找到真正的写点

## 27. 观测手段升级：32 位调试器助手

64 位 Python 调试 32 位 WOW64 进程时 DR 寄存器不生效（只会碰到 WOW64 转换层的单步）。
改为 **i686 原生助手** `cmykdrop/hwbp32.c`（`SetThreadContext` 直接作用于 32 位上下文），
用法：

```
hwbp32.exe <目标exe> <工作目录> <监视地址hex> <秒> <命令表> <日志>
```

实测：带狗跑 120 秒 → **309 次命中**，证明这套观测对动画**零干扰**
（同一次运行临时目录仍是 1263~1285 个文件）。

## 28. `off` 的真正写入点（硬件断点实测）

| 场景 | 命中 Eip | 实际写指令 | 公式 |
|---|---|---|---|
| 导入psd | `00504D9C` | `0x504D92: mov [0x523090], 0x3c` | off=60 定值 |
| **带狗 预览** | `00509038` | **`0x509033`** | `off = 20 + round(K*i/N)`，**+7/帧，持续循环** |
| 无狗 预览 | `005055CE` | `0x5055C9` | `off = 10 + round(K*i/N)`，**+8/帧，只走一轮** |

两条不同的循环：`0x509033` 所在的是**完整渲染循环**（会生成 1188 张逐层切块 `*gx*.gjs`），
`0x5055C9` 所在的是**轻量预览循环**（只画屏幕位图）。**这就是画面错的直接原因**。

## 29. 顺带解决：视图数

`off` 循环的边界来自 `[0x5230FC]`，而这个值最终来自 `psdto3d104.inf` 第 2 行第 2 个数
（也对应界面那个 Edit）。把 inf 里的 ` 7 ` 改成 ` 11 ` 之后：

```
命中 12 次 = 1 次导入 + 11 步动画（esi/edi 依次 0..10）
临时目录：ly 32 / lyt 32 / vw 11 / vwt 11   ← 预览位图从 7 张变 11 张
```

## 30. 仍未解决 + 下一步

- `vwd` 已能出 11 张，但与实机逐像素差 **22.6~26.5/255**（结构对、细节错）。
- 加回「导入设置」没有帮助：在本环境它必然报 `Invalid numeric input` 并中止
  （那是 exe 自身的装载器 bug，与狗无关），所以它不是两条循环的开关。
- **下一步唯一动作**：用 32 位助手分别断在 `0x509033` 与 `0x5055C9` 所在的**函数入口**，
  记录 `stack[0]`（返回地址），把两条分支的调用者求出来 —— 那个分支条件就是把
  "轻量预览" 切成 "完整渲染" 的开关。
  （helper 里的栈打印这段目前被 `IsBadReadPtr` 挡住，需要先修掉。）

# 续查 6（2026-11-19 08:37–09:05）：填表被"重建记录"冲掉 + 首次进入完整渲染

## 31. 两条路径的分叉点（硬件断点调用链，实锤）

| | frame[0] | frame[1] | 结论 |
|---|---|---|---|
| 带狗 | `0050DE53` | `0050AF6E` | `0x50AF69 call 0x50D9AC` **被调用**（逐层渲染 → `0x509033`） |
| 无狗 | `0050AF7B` | `0050B02B` | 循环**直接到末尾**，一次都没调（走 `0x5055C9` 轻量路径） |

唯一判据：`0x50AF42: cmp byte [rec+i*56+0x2C], 0xFF`。

## 32. 记录表被"重建"冲掉（这是关键）

`+2C` 高频跟踪（仿真器 iatpatch 线程）：

```
FILL 已填 32 条 → ST t=14  +2C = FFFFFFFF…FF     ← 我们写入成功
                → ST t=15  +2C = 00000000…00     ← 1 秒内被清回 0
```

再用 `rec+2C` 看门狗（按记录表基址+偏移设单字节断点）抓到清零者：

```
#2 t=13.38 eip=744649ED  eax=028230E0(监视地址)  ebx=0x20(32)  edx=02823000
```

即**导入后程序会把整块记录区重建一遍**（批量写），我们的 FF 被覆盖。指针本身只被写过一次
（`SetLength(32)`，`edx=0x700`），所以不是重新分配，是原地重建。

## 33. 改成"持续守护"后：**第一次进入完整渲染**

`fill_thread` 由"填一次"改成"只要又变全 0 就重填"。结果：

```
temp: ly 32 / lyt 32 / #gx# 11 / #gxt# 11 / #xgx# 11 / #xgxt# 11
      ↑ 逐层逐视图切块开始出现（此前从未有过）
```

但随后报 `Invalid pointer operation.`（用 VirtualAlloc 造 `g230` 的 32 个实体时），
改用 `borlndmm!@Borlndmm@SysGetMem$qqri` 分配后又变成更早的 AV `004061C8`（读 `003365FC`）。

## 34. 结论与下一步

- **分叉点、清零者、填表时机**三件事都已实锤，剩下的只是"如何让 `g230` 的 32 个实体
  被程序当作合法对象"。
- 带狗时这些实体是 0x48 字节连续、内容几乎全 0、只有几个指针；既不是纯 VirtualAlloc
  （会被 FreeMem 报错），也不是简单 SysGetMem 一块（RTL 读长度时越界）。
  → 下一步：用 `rec+2C` 那套看门狗改成监视 `g230[k]` 的**写入**，看程序对实体做什么
  （是 FreeMem、还是写对象头），照它期望的形状分配。

# 续查 7（2026-11-19 09:00–09:35）：装载器计数补丁做对了，但露出下一个 bug

## 35. 正确修掉"计数"这件事

上一轮的 `patch_layout_count`（把 `[ebp-0x60]` 换成 `[ebp-0x54]`）**是错的**，本轮量化证明：
补丁后循环跑出第 **69** 条记录（`AV 0x511ADC Write of address 027B4000`，
而数组只有 32×56=1792 字节）。

正确做法：用 `[0x52315C]`——导入 PSD 后它就是层数（记录表正是按它 SetLength 的）。
实现用代码洞 `0x514324`（220 字节全 0）：

```asm
; 0x511A03 原: mov eax,[ebp-0x60]
00511A03  jmp 0x514324
00514324  mov eax,[0x52315c]
00514329  test eax,eax
0051432B  jl 0x511a81
00514331  jmp 0x511a0a
; 0x511A81 同样处理，桩在 0x514340
```

工具：`tools/patch_loader_count2.py`（幂等，会先检查洞是否为空）。

## 36. 结果：错误往前推进了一步

| 版本 | 「导入设置」的表现 |
|---|---|
| 原始 exe | `Invalid numeric input`（令牌流错位） |
| 旧补丁 `[ebp-0x54]` | `AV 0x511ADC`（写到第 69 条记录，越界） |
| **新补丁 `[0x52315C]`** | **`List index out of bounds (-1)`** |

也就是说：**行块计数已经正确、令牌流不再错位**，现在撞到的是装载器后面另一处
"用 -1 去索引一个 TList"的 bug（很可能是某个按分组建的表长度为 0 时仍取 `[count-1]`）。

## 37. 下一步

用 `hwbp32` 在 Delphi 抛错的那一刻停下（`Error(reListIndexError)`，或直接对
`0x403xxx` 的 raise 例程下断），抓调用栈就能定位是哪个 List 为空。
工具链都现成：`cmykdrop/hwbp32.c` 已支持任意地址的读写断点 + EBP 链回溯。

# 续查 8（2026-11-19 10:40–11:25）：反验证——所谓 bug 是不是狗检测

## 38. 方法论（LO 定的）

> 所有觉得有 bug 的地方都可以合理怀疑是狗检测导致的，去做反验证，而不是当成 bug 强行修复。

本轮按此执行，结论如下。

## 39. 反验证一：图层顺序 —— 排除

`gx` 逐层逐视图切片共 **1188 张**，带狗 A 组 vs 无狗 B 组：
**逐字节全同**（抽样 200 张内容亦全同）。

→ 图层顺序、角度、分组、缩放、包围盒全部一致，**"顺序搞错"不成立**。

## 40. 反验证二：预览位图 —— 确认是视差量差异

| 视图 | mean |
|---|---|
| vw6（正中心） | **0.0000 全同** |
| vw5 / vw7 | 4.57 / 5.16 |
| vw3 / vw9 | 7.41 / 8.31 |
| vw1 / vw11 | 9.46 / 10.35 |

以中心严格对称、越靠边差越大 —— **视差步长差一点**，不是错乱。

两条路径的公式（反汇编）：

```asm
0x509033（带狗完整渲染）: off = 20 + round(80 × (i-1) / 11)
0x5055C9（无狗轻量预览）: off = 10 + round(90 × i     / 11)
```

## 41. 反验证三：狗应答重放 —— 失败且有害

把带狗录下的 8 条 501 应答头做成命令匹配表，命中就整块覆盖：
**画面从 7.10 退化到 20.13**。原因：无狗时程序发的命令序列与带狗不同，
第一对 `7B 00 00 00` 是启动握手，重放等于喂错数据。

## 42. 重要发现：这份"完整日志"其实不完整

`_review/licensed_scsi_full.log` 只有 74 行，覆盖到「导入设置」后保存 out.tif，
**没有预览阶段的狗事务**。重新录了一次带狗预览会话（`_review/pkgA/_dongle.log`，55 行），
证实：**预览渲染阶段根本不问狗**（日志到 #5 那条命令后就中断）。

→ 之前"狗在预览时提供参数"的推断在此日志中**没有证据**，已撤回。

## 43. 关键 bug：分类条件把层数查询判丢了

仿真器 `h_dio` 里按 `p2 >= 0x00400000`（ptr2 是否指向代码段）分类。
但层数查询命令的 `ptr2 = cmd[6..9] = D5 0F xx xx` → 值约 `0x025A0FD5`，
**小于 0x400000**，被判成"参数型"，于是层数计算代码从未执行。

带狗实测该命令的应答：
```
write: 02 00 00 00 | 02 00 00 00 | 20 00 00 00 | 00 00 00 00 | 00 00 00 00
resp : 02 00 00 00 | 02 00 00 00 | 20 00 00 00 | 00 00 00 00 | 20 00 00 00 | 1F 00 00 00
                                                   ↑write[2]=32  ↑31=层数-1
```
即 `resp16 = write[2] = 层数`、`resp20 = 层数-1`。

已在 `dongle_fake.c` 加了前置判定（`cmd[6..7]==D5 0F` 优先拦截）。
但实测这一改**反而使预览从 7.10 退化到 20.13** —— 说明 fake22 达到 7.10
走的是另一条路径（可能是 `FILL_PROJ` 填表 + 装载器自然成功），不是靠这条命中。
**当前基线仍用 fake22（7.10）。**

## 44. 现状与下一步

- 基线：`cmyktiff2_fake22.dll`，预览 vw6 全同、两侧 4.5~10.4
- 已确认：gx 全同、预览不问狗、两条公式不同
- 未确认：到底是什么决定了"走 20/80 那条完整渲染公式"而不是 "10/90 轻量公式"
  —— 下一个实验：在两条公式各自的入口（`0x509033` / `0x5055C9`）同时下断点，
  用**同一次无狗运行**记录它们各被调用多少次、以及进入前的判据寄存器。
