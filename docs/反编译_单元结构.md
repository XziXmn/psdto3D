## 1. 类层次：`vmtParent` 的正确换算（A 级）

Delphi 7 的 VMT 相对基址：

| 偏移 | 字段 |
|---:|---|
| −76 | `vmtSelfPtr`（指向自身） |
| −52 | `vmtMethodTable` |
| −44 | `vmtClassName`（指向类名 ShortString） |
| −40 | `vmtInstanceSize` |
| **−36** | **`vmtParent`** |

**踩到的坑**：`vmtParent` 存的不是父类 VMT 基址，而是**父类「自指针字段」的地址**，
也就是 `parent_vmt − 76`，必须 `+76` 才得到父 VMT。

验证（`psdto3d101.exe`）：

```
TForm1  vmt = 0x004FDAE0    dword[vmt-36] = 0x00475F68
TForm   vmt = 0x00475FB4    0x00475FB4 - 76 = 0x00475F68   ← 完全吻合
```

按此换算后，三个模块都只剩**单一根类 `TObject`**，父链正确：

```
TForm1          → TForm → TCustomForm → TScrollingWinControl → TWinControl
                → TControl → TComponent → TPersistent → TObject
TStringList     → TStrings → TPersistent → TObject
```

规模：

| 模块 | 类总数 | 根类 |
|---|---:|---|
| `psdto3d101.exe` | 358 | `TObject` |
| `cmyktiff2.dll` | 165 | `TObject` |
| `8602.dll` | 239 | `TObject` |

## 3. 规划点名的 9 个业务单元：只命中 1 个

| 单元 | 是否出现在注册表 |
|---|---|
| `GraphicEx` | ✅ 14 个类 |
| `GMMSystem` | ❌ |
| `KWindows` | ❌ |
| `UTypes` | ❌ |
| `XVCF1` | ❌ |
| `FComObj` | ❌ |
| `YStrUtils` | ❌ |
| `GraphicColor` | ❌ |
| `MZLib` | ❌ |

**原因**：类注册表只包含用 `RegisterClass` 注册过的类——即**窗体与可视组件**。
`GMMSystem`、`KWindows` 这类纯逻辑单元没有 published 类，不会出现在注册表里，
它们的函数也就拿不到单元归属。

因此 C4 的「业务单元命名覆盖率 ≥70%」在这条路上**只能覆盖 `GraphicEx` 一个**。
要覆盖其余 8 个，仍需 Delphi 的**单元初始化表**（把 `unitinit_*` 与 PACKAGEINFO 顺序对齐），
而该表本轮仍未定位（`.DATA` 里 5 个候选指针表与 75 个 `unitinit_*` 地址零命中）。

1. **窗体单元划分已确定**：主窗体是 `Unit1`，各对话框独立成单元

## 6. 单元初始化表的追查结果（本轮新增，C 级）

### 6.1 查到的东西

`DelphiInit.java` 用模板 `55 8B EC 33 C0 55 68` 在 `psdto3d101.exe` 里找到 75 个函数。
检查它们的地址在本文件里被引用的情况：

- **75 个地址各被引用恰好一次**，全部集中在文件偏移 `0x113300` 附近；
- 转成 VA 后，是一张从 **`0x513F70`** 开始的连续指针数组，其前 4 字节（VA `0x513F6C`）
  存的是表首自身地址（`0x00513F70`），符合「表指针 + 表体」的形态；
- 表项全部指向 CODE 段，范围 `0x0040737C .. 0x00513CF0`。

### 6.2 但它不是纯净的单元初始化表

| 观察 | 数值 |
|---|---|
| 表项总数（连续扫到非代码指针为止） | **192** |
| 与语料里 `unitinit_*` 完全重合 | **73 / 75** |
| 表项正好等于某个已知函数起点 | 96 / 192（约 50%，且从头到尾均匀） |

PACKAGEINFO 里 `psdto3d101.exe` 的单元数是 **79**，与 192 差得很远；
命中率均匀 50% 说明表项也指向函数内部，**不是「每单元一个 init 入口」的排布**。

**判断（C 级）**：这更像一张通用的代码指针表（异常帧表或资源表），
不能直接用来把「PACKAGEINFO 的单元顺序」映射到「init 地址」。

### 6.3 对 C4 的影响

规划点名的 8 个纯逻辑单元（`GMMSystem`/`KWindows`/`UTypes`/`XVCF1`/`FComObj`/
`YStrUtils`/`GraphicColor`/`MZLib`）**仍然无法归因**，因为：

1. 类注册表只含可视类，这 8 个单元没有 published 类（见第 3 节）；
2. 单元初始化表的边界与语义未能确定（本节）。

要继续推进，只有两条路，都需要额外前提：
- 找到 Delphi 7 编译器在 `System` 里维护的 `InitTable` 的**准确布局与条目类型**（需要同版本编译器样本做对照）；
- 或者放弃自动归因，改成对候选函数做**人工判读**（工作量按千计）。

### 6.4 可复现

```bash
python - <<'PY'
import struct, pefile
from pathlib import Path
p='Psdto3d/psdto3d101.exe'
pe=pefile.PE(p, fast_load=True); base=pe.OPTIONAL_HEADER.ImageBase
raw=Path(p).read_bytes()
def off_of(va):
    for s in pe.sections:
        sva=base+s.VirtualAddress
        if sva<=va<sva+max(s.SizeOfRawData,s.Misc_VirtualSize):
            return s.PointerToRawData+(va-sva)
va=0x513F70; out=[]
while True:
    o=off_of(va)
    if o is None: break
    v=struct.unpack_from('<I', raw, o)[0]
    if not (0x401000<=v<0x514400): break
    out.append(v); va+=4
print(len(out), hex(out[0]), hex(out[-1]))
PY
```

## 9. 规划点名的 9 个业务单元：全部找到（第 46 轮）

此前判断「这 9 个单元只有 `GraphicEx` 出现在 IDR 的单元表里」。本轮改用 **PACKAGEINFO 扫描**，
结果 **9 个全部命中**，而且分布在各个模块里：

| 单元 | 出现在哪些模块 |
|---|---|
| `GMMSystem` | `psdto3d101.exe` |
| `XVCF1` | `8602.dll`、`psdto3d.exe`(99)、`psdto3d101.exe` |
| `FComObj` | `8602.dll`、`psdto3d.exe`(99)、`psdto3d101.exe` |
| `KWindows` | **14 个模块全部**（含 `zu6`、`zu61`、`dspr`、`ok3d1`、`ok3d4`、`save3d`、`3d99`、`G3d99`、`KeyReg101`） |
| `UTypes` | 同上 14 个 |
| `YStrUtils` | 11 个模块 |
| `GraphicColor` | 7 个（`8602`、`dspr`、`psdto3d.exe`、`psdto3d101.exe`、`zu06`、`zu6`、`zu61`） |
| `GraphicEx` | 同上 7 个 |
| `MZLib` | 同上 7 个 |

### 9.1 为什么 IDR 的单元表里看不到它们

IDR 的 Units 列表是**能定位到代码的单元**；`KWindows`/`UTypes` 这类在 exe 里可能只有接口引用、
没有独立代码段，于是落到 IDR 的 30 个 `_UnitNN` 里去了。

**PACKAGEINFO 给名字，IDR 给地址——两者信息互补。**

### 9.2 试过但失败的思路：按顺序对齐给 `_UnitNN` 命名

想法很自然：PACKAGEINFO 是**注册顺序**，IDR 是**地址顺序**，若能对上就能给 30 个
`_UnitNN` 补名字。

实测（exe，两者共有 24 个单元）：

```
Spearman 秩相关 = 0.480
```

**中等相关，不足以插值。** 反例很明显：

| 单元 | PACKAGEINFO 序 | IDR 地址序 |
|---|---:|---:|
| `psdto3d101` | **#0** | **#66（最后）** |
| `SysConst` | #8 | #3 |
| `OleServer` | #10 | #57 |

工程的 `.dpr` 单元在注册顺序里排第一、在地址上排最后，这一项就把相关性拉垮了。

**结论：此路不通。** 记录在此，避免以后重复尝试。要给 `_UnitNN` 命名，
需要另外的线索（例如各单元的字符串引用、初始化代码特征）。
