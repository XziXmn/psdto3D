- 验收工具 `tools/accept_check.py`：逐层比对 RGB 与 alpha，PASS 阈值「层均值≤4.0、中心区≤0.5、alpha≤1.0」

### 2.2 查清两个"画面错"的真实原因

1. **工程第 1 行 PSD 路径长度**：113 字节时报 `Can not found the specified psd file!` 且**不弹窗**（只写状态栏），随后所有参数静默回退默认值。改成 46 字节路径即正常。
2. **必须执行「导入设置」**：只做"导入PSD + 预览"时，层记录里的 `+0x2C` 一直是 `0x00`，渲染走的是另一条分支，画面是"平的"。执行 10 之后 `+0x2C` 变 `0xFF`，视差才生效。

证据：`证据截图\2026-11-18复查\01~05`。

### 2.3 加密狗的真面目（这是无狗路线的总钥匙）

USBKey 走 SCSI_PASS_THROUGH（`IOCTL_SCSI_MINIPORT`，控制码 `0x0004D014`），CDB `op=0xDD` 写 / `0xD1` 读。

一次完整事务：

```
写 496 字节（程序自己的内存块，含 0x7B 头）
写 26 / 42 / 58 / 104 / 112 / 194 字节（模块密钥材料）
写 10 字节命令
读 501 字节应答 + 5 字节 ack
```

应答只有两类：

| 类型 | 结构 |
|---|---|
| **回显型** | `16 × (7B 00 00 00)` + **刚写入 496 字节块的 [16:496]**（480 B）+ `FB 00 00 00 00` |
| **计算型** | 在写入的参数块上改个别 dword 后返回（例：`0x834→0x402`、`3→0x8A4`） |

**关键认知**：它不是加密芯片，是"你把内存给我、我加个头还给你"的**回显校验器**。
之前所有"回放录制数据"的仿真都失败，原因是回放返回的是**别的进程**的内存，程序一比对就不是自己的，于是走坏分支 → `AV 0x50A001`。

按回显模型重写后，**`0x50A001` 这个必崩彻底消失**（此前 4 种配置必崩）。

### 2.4 绕过「导入设置」的填表器

`cmykdrop/fillrec.c`：解析 `.tw3d2`，直接写 56 字节层记录表。

| 偏移 | 含义 | 来源 |
|---|---|---|
| `+0x2C` BYTE | 状态：`00` 未初始化 / `FF` 已读入 / `64` 预览派发中 | 固定写 `FF` |
| `+0x2D` BYTE | 角度 | 工程每层表第 1 列 |
| `+0x2E` WORD | 分组 | 第 2 列 |
| `+0x30` DWORD | 缩放 ×10000 | 第 3 列 |

全局：`f0fc`(`0x5230FC`)=视图数=工程第 2 行第 2 个数；`amp`(`0x52308C`)=40、`off`(`0x523090`)=60 由「导入PSD」自己设好，不用碰。

### 2.5 复刻了「导入设置」创建的两个内部对象

带狗实测：执行 10 之后多出

- `g230`(`0x523230`)：**32 个指针**，每个指向一个 72 字节空壳（地址间隔 0x48）
- `g218`(`0x523218`)：5 个 dword = `[919, 488, 353, 796, 228]`

而逐层渲染循环第一句就是 `edx=[0x523230]; edx=[edx+ebx*4]` —— **空指针必读地址 0，动画第一帧就死**。造出来后预览不再崩，`vwd` 能出。

### 2.6 定位了两条渲染路径的分叉点（硬件断点实锤）

用 32 位原生调试助手 `cmykdrop/hwbp32.exe`（DR0 监视，不改代码字节，对动画零干扰——同一次运行临时目录照样 1263~1285 个文件）：

| | 调用链 | 含义 |
|---|---|---|
| **带狗** | `frame[0]=0050DE53`、`frame[1]=0050AF6E` | `0x50AF69 call 0x50D9AC` 被调用 → **完整渲染**，`off` 由 `0x509033` 写（`20+round`，+7/帧，持续循环），生成 1188 张逐层切块 |
| **无狗** | `frame[0]=0050AF7B`、`frame[1]=0050B02B` | 循环**直接到末尾**，`0x50D9AC` 一次没调 → **轻量预览**，`off` 由 `0x5055C9` 写（`10+round`，+8/帧，只走一轮） |

唯一判据就是这一句：

```asm
0050AF42  cmp byte ptr [edx + eax*8 + 0x2C], 0xFF
0050AF47  jne 0x50AF6E          ; 不是 FF → 跳过这一层
```

### 2.7 查清"填了又被冲掉"

`+0x2C` 高频跟踪：

```
FILL 已填 32 条 → t=14  +2C = FFFF…FF   ← 写入成功
                → t=15  +2C = 0000…00   ← 1 秒内被清回 0
```

用「记录表基址+偏移」的单字节看门狗抓到清零者：

```
#2 t=13.38  eip=744649ED  eax=028230E0(监视地址)  ebx=0x20(32)  edx=02823000
```

**导入完成后程序会把整块记录区重建一遍**（批量写），把 `FF` 覆盖掉。记录表指针本身只被写过一次
（`SetLength(32)`，`edx=0x700`），所以不是重新分配，是原地重建。

对策：`fill_thread` 由"填一次"改成**持续守护**——只要又变全 0 就重填。
效果：**第一次进入完整渲染路径**，临时目录开始出现 `#gx# / #gxt# / #xgx# / #xgxt#` 四族切块。

### 2.8 修正了装载器的"行块计数" bug

历史结论里的补丁（把 `[ebp-0x60]` 换成 `[ebp-0x54]`）**是错的**，本轮量化证明：

```
旧补丁 → 循环跑到第 69 条记录
崩溃地址 027B4000 − 记录表基址 027B30B4 = 0xF4C = 3916 字节
数组容量 = 32 × 56 = 1792 字节（0x700）
```

正确做法：用 `[0x52315C]`（导入后就是层数）。代码洞 `0x514324`（220 字节全 0）里放桩：

```asm
00511A03  jmp 0x514324          ; 原: mov eax,[ebp-0x60]
00514324  mov eax,[0x52315c]
00514329  test eax,eax
0051432B  jl  0x511a81
00514331  jmp 0x511a0a
; 0x511A81 同样处理，桩在 0x514340
```

工具：`tools/patch_loader_count2.py`（幂等，先校验洞是空的）。
效果：错误从 `Invalid numeric input`（令牌流错位）**前移**到 `List index out of bounds (-1)`。

### 2.9 视图数这件事

- 视图数最终来自 `psdto3d104.inf` **第 2 行第 2 个数**，也对应界面那个 Edit（`0x50AE1A: call 0x409b08` 每帧现读）
- 把 inf 里 ` 7 ` 改成 ` 11` 后：动画走满 11 步（`esi/edi` 依次 0..10），`vw/vwt` 从 7 张变 11 张

## 3. 未完成

### 3.1 唯一硬卡点：`List index out of bounds (-1)`

「导入设置」现在跑到一半抛这个错（弹 `#32770` 对话框，说明走的是 `MessageBox`）。含义是某处拿 `-1` 去索引一个 TList，很可能是"按分组建的表长度为 0 时仍取 `[count-1]`"。

它挡住的东西：程序内部对象（`g230`/`g218` 等）无法由程序自己正规创建，只能靠我们伪造；而伪造的实体不被程序认可：

| 分配方式 | 结果 |
|---|---|
| `VirtualAlloc` 造 32 个 72 字节实体 | 进入完整渲染、切块出来 11 组后报 `Invalid pointer operation.` |
| `borlndmm!@Borlndmm@SysGetMem$qqri` 分配 | 更早 AV：`0x4061C8`（`DynArrayLength`，读 `[eax-4]`）拿到垃圾 |

### 3.2 次要缺口（重写路线才需要）

- PSDTO3D 写出的 PSD **没有 ICC 配置文件、没有 ResolutionInfo(ID 1005)**；你的 `LenticularOmega` 下游需要这两样，目前是靠写出的 TIFF 里 XRes 277.2 / YRes 138.6 反推 DPI（4370×5197 → 180.4×214.0 mm）
- 计算型狗应答的变换算法还没还原（只影响"完全理解协议"，不影响带狗使用）

## 4. 关键机制速查（给下一个人）

### 4.1 PE / 保护

- `psdto3d101.exe`：Delphi/VCL 32 位，imagebase `0x400000`，入口 `0x514278`，代码节名 `CODE`
- **没壳**（CODE 熵 6.61）、**没反调试**（无 `IsDebuggerPresent` / `NtQueryInformationProcess`），`.tls` 回调表全 0
- 结论：可以放心用调试器与硬件断点

### 4.2 关键全局

| 地址 | 含义 |
|---|---|
| `0x52315C` | 层数（=记录数） |
| `0x5230B4` | 56 字节记录数组指针 |
| `0x5230FC` | 视图数（每帧从界面 Edit 现读） |
| `0x52308C` / `0x523090` | 视差幅度 `amp` / 基准 `off` |
| `0x523203` / `0x523204` | 预览使能 / 帧推进标志 |
| `0x523230` / `0x523218` | `g230`（32×指针）/ `g218`（5 dword） |
| `0x523170` | 由界面数值算出的节流阈值（`fistp`） |

### 4.3 工程文件（.tw3d2）

```
第1行  PSD 绝对路径（尽量短！）
第2行   LPI  视图数  X  深度  ...（第2个数是视图数）
第3行  99100 | 39550  层数  宽  高
第4..3+N 行      每层一个整数
第4+N..3+2N 行   每层 " 角度 分组  缩放"
其后            曲线块（"图层 分组 子序号 点数" + 折点）
```

### 4.4 渲染链路

```
预览/输出
 ├─ 0x50AD74 处理函数
 │   └─ 0x50AF26 逐层派发循环
 │        └─ 若 +0x2C == 0xFF → 置 0x64 → call 0x50D9AC（真正画这一层）
 │             └─ … → 0x509033 写 off = 20 + round(K*i/N)
 └─ 否则 → 0x50AF7B → 轻量预览 → 0x5055C9 写 off = 10 + round(K*i/N)
```

逐层切块文件名：`<层号>gx<视图号>.gjs`（另有 `gxt` / `xgx` / `xgxt` 三族变体），最终由导出函数合成 `vwd<视图号>.gjs`。

## 8. 坑（别踩）

1. **不要用代码补丁做观测**。本轮实测：在 `0x5055C9` 等函数体内打 5 字节补丁，会把预览动画本身弄挂（Delphi 对指令边界/栈帧敏感），于是"看起来动画不跑"，得出错误结论。要用硬件断点（`hwbp32.exe`）。
2. **64 位 Python 调试 32 位进程时 DR 寄存器不生效**（只会碰到 WOW64 转换层的单步）。必须用 32 位助手。
3. **`hwbp32` 读取目标内存要用 `ReadProcessMemory`**，不要用 `IsBadReadPtr`（那查的是调试器自己的地址空间）。
4. **`DO_CLEAR` 式的周期性内存清零必须保持关闭**，它会破坏 `borlndmm` 堆（`AV 0x0076460B`）。
5. **不要把"槽位轮转"当成狗协议**。那是早期仿真的自造规则，已证伪。
6. **临时目录 `C:\ok3dtemp` 每次跑之前要清空**，否则文件计数时间线会误导。
7. **`psdto3d104.inf` 会被程序回写**（退出时保存设置），做实验前先备份。
