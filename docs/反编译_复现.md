> 目的：让「源路径 → 哈希 → 语料目录 → 覆盖率」这条链**可一键核对**。
> 全部脚本在 `_analysis/`，全部产物在 `_analysis/` 与 `docs/`；
> `Psdto3d/` 等原始目录始终只读。

## 1. 一键自检

```bash

```

它做四件事：

1. 扫描 8 个语料目录的 `index.tsv`，重算函数数与函数体字节；
2. 重算源 PE 的 SHA-256，与 `baseline.json` 比对；
3. 重算覆盖率，与 `coverage.tsv` 逐行比对；
4. 报告反编译失败数。

## 1b. 文档一致性自检

```bash
python -I _analysis/check_docs.py
```

检查三类断言：

1. 文档里引用的 `dump_*` 语料目录是否存在；
2. 引用的语料是否仍属于该模块（同一文件名家族的任一行都算有效）；
3. 文档里出现的覆盖率百分比是否都能在 `coverage.tsv` 里找到对应取值。

当前输出：

```
文档中引用的语料目录全部存在；
覆盖率数值集合与 coverage.tsv 一致（15 个不同取值）。
```

非本会话的文档（如 `复查交接文档.md`）只作提示，不参与判定。

## 1c. 用 REA 做独立对照

REA（`rea@6.9.0`，内置 Ghidra 12.2）可作第三方读数，核对本仓库的函数发现量：

```bash
rea analyze Psdto3d/psdto3d101.exe --provider ghidra --format json --filter-output normalized_result
rea search  Psdto3d/psdto3d101.exe FUN_ --kind procedures --mode literal --provider ghidra --format json --full-output
```

实测对照（同一二进制、同一 Ghidra 版本）：

| 模块 | REA 默认 | 本流水线 |
|---|---:|---:|
| `psdto3d101.exe` | 5,327 | 7,100 |
| `cmyktiff2.dll` | 3,222 | 3,850 |
| `zu06.dll` | 3,566 | 4,319 |

REA 的过程地址是本流水线的**严格子集**；工程读写与窗体处理器那批函数
恰好不在 REA 清单里（它不做 Delphi VMT 方法发现）。
详见 `docs/反编译_进度.md` 的「REA 交叉验证」一节。

## 2. 从零重建某个模块的语料

```bash
G="C:/Users/moo/AppData/Local/Programs/ghidra/ghidra_12.2_PUBLIC"
S="C:/Home/Workspace/UGit/psdto/_analysis/ghidra_scripts"

analyzeHeadless _analysis/ghidra_proj <工程名> \
  -import "<模块绝对路径>" \
  -scriptPath "$S" \
  -postScript DelphiSEH.java \
  -postScript DelphiInit.java \
  -postScript DelphiVMT.java "<vmt 输出 tsv>" \
  -postScript DelphiSweep2.java \
  -postScript DelphiSweep4.java \
  -postScript DelphiSweep6.java \
  -postScript DumpAll.java "<语料输出目录>" \
  -deleteProject
```

### 两个必须知道的坑

1. **路径含空格或括号会失败**：`Psdto3d (2)/psdto3d101.exe` 直接传会让
   `analyzeHeadless.bat` 报 `\psdto3d101.exe was unexpected at this time.`（exit 1 且无输出）。
   做法是复制到 `_analysis/tmp/` 再导入，并记录 SHA-256 保持溯源。
2. **索引文件是边写边增长的**：headless 报「完成」后 `index.tsv` 还会继续变大
   （实测 3,337 → 4,915 → 5,736 → 7,053）。**必须轮询到行数稳定再读数**，
   否则会得到偏低的函数数与覆盖率。
