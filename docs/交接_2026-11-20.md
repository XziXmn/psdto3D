## 二、加密狗（USBKey）

- 形态：U 盘式加密锁，VID `1312` / PID `2012`，1,049,088 字节，无卷。
- 通道：SCSI 直通（`IOCTL 0x4D014`）到 `\\?\usbstor#disk&ven_usbkey&...`。
- 请求：**10 组「写 + 读」成对**。

| # | 写 | 随后的读 | 读回长度 |
|---|---|---|---|
| 1 | `DD 496 @0` | `D1 496 @0` | 5 |
| 2 | `DD 26 @0` | `D1 26 @0` | 5 |
| 3 | `DD 10 @0x1F0` | `D1 10 @0x1F0` | 501 |
| 4-6 | 同 1-3 再来一轮 | | |
| 7 | `DD 0 @4` | `D1 0 @4` | 9 |
| 8 | `DD 496 @0` | `D1 496 @0` | 5 |
| 9 | `DD 42 @0` | `D1 42 @0` | 5 |
| 10 | `DD 10 @0x1F0` | `D1 10 @0x1F0` | 501 |

- 44 字节 SPT 头：`TargetId=1`、`CdbLength=16`、`CDB[1]=0xFE`、`SenseInfoOffset=0x30`。
- 读的 CDB = 写的 CDB 首字节 `DD`→`D1`，其余完全一致。
- 501 字节应答 = `7B×16` + 写入块[16:] 回显 + 设备改动的 23 字节
  （偏移 `16, 20, 24, 28, 77..95`，**跨运行完全稳定**）。
- 其中 `16=层数`、`20=层数-1`、`24/28=ceil(层数/16)`；`77..95` 随运行变但未见于任何消费点。
- 10 字节命令每次运行都不同（`000010FA` / `0000F33E` / `00005F23`），故**录制回放不可行**。

### cm 完整公式（实测确认）

```
A = 网格(行来自 [ebx+0x530], 列 2)     ; 实测 A 行恒为 13
B = 网格(行 = [0x52315c] - esi, 列 2)
g4 = (25400 / 3000000) × [0x523074] / 1500000 × [0x523190]
cm = round((B - A) × 100 × g4 / 10000) / 100
```

`[0x523074] = 25400 × (层数-1) = 787400` 时 g4 = 79.99984 ≈ 80，
代入 (B-A) = -5 得 **-0.04**，与真狗基准完全一致。

### 关键教训

- `hwbp32.exe` 的双地址 `exec@A,B` 不可靠，只用单地址；
- 在 `0x48D628` 处读字符串要用 `[esp+4]`（`[esp]` 是返回地址）；
- 硬件断点单次命中不会自动重复，循环体上的断点会命中每一轮（已验证 `0x511A79` 命中 32 次）；
- 插入 cave 时**不要覆盖循环尾指令**，否则会静默打断循环（本次踩过）。

## 十、cm 的确切死因（2026-11-21 00:00）

### 实测

```
0x513AAA  cmp dword [ebp-8], 0 ; je 0x513BDF   ← 命中 1 次，v8 = 0
```

`[ebp-8]` 是网格读取（`0x48D5B8`）的返回值。它返回 **0**，cm 立刻跳到出口，
一个格子都没写。这解释了此前所有现象：

- cm 从未写过第 3 列（之前把 `00512671` 等组的写误当成 cm 的写，实际是 0/1/2 列）；
- 换挂点、换调用时机、补倍率、改行号全部无效——cm 根本没走到计算。

### 根因

```
读 0x48D5B8 → 0x48C768           只管查，查不到返回 0
写 0x48D628 → 0x48D564           查不到时，还要过一道门：
   0x48D57E  cmp dword [ebx+0x21C], 0x200
   0x48D588  jle ...             ← 不大于就直接返回，不创建行
```

即：**行不存在时写操作会静默跳过**。所以「17 字符的写入」实际没落盘，读回来自然是 nil。

### 尝试与结果

在桩里补调 `0x48D6C8`（四个访问器中的第四个，带 SEH 帧，疑似 RowCount setter）设置行数 32：
**AV = 0 但仍无第 3 列写入**，说明它要么不是 RowCount，要么调用时机太早（此时网格尚未准备好）。

### 当前交付文件

```
_work\v2\psdto3d101.exe   md5 = 01e03d65e13e0c980ffb60a3e2243c47
AV = 0 ；Offset 五行写入 17 字符值 ✔
```

### 下一步建议

1. 确认 `0x48D6C8` 到底是哪个属性（看它的属性索引常量），或找到真正的 RowCount setter；
2. 或直接在 `0x48D564` 的门槛 `0x48D588` 处把跳转改成「总是创建行」，让写入落盘；
3. 之后 cm 的读就能拿到值，公式（g4=80）已完全就绪。

## 十一、关键更正：狗不提供任何数字（2026-11-21 00:50）

全量反编译（`_work\re_all`，4816 个函数）后，解析器 `0x4D2F14` 的伪代码说明了真实机制：

```c
FUN_004d24e8("opensaveset.enc.lll", &local_10);        // 只是拼出 <程序目录>\opensaveset.enc.lll
pCVar3 = FUN_00405410(local_10);
uVar4 = FUN_004e32fc(path, ..., pcVar7..pcVar2, ...);   // 传入 8 个参数字符串
if (uVar4 == 0 || uVar4 == -43 || uVar4 == -67) {
    FUN_004051c0(param_11, local_42, 0x32);             // 原样拷回
    ... 共 8 个
}
```

**结论**：8 个输出就是 8 个输入的**原样拷贝**，没有解密、没有变换。
狗返回 0/-43/-67 时，程序就把这些值放行；否则不拷贝。

所以：
- **狗不提供层数、循环计数、倍率**（此前的表述有误，已更正）；
- 这些值全部来自工程文件，明文；
- 狗的作用只是"是否放行"这一道判定。

`0x4E75E0` 也已确认只是 `GetModuleFileNameA` + 截出目录，与密钥无关。

## 剩余疑问（下一步唯一要查的）

判定放行后（v3 改良版），`0x511A73` 一次都没命中，说明装载器没走到 Offset 循环。
需要确认：装载器传给 `0x4D2F14` 的那 8 个参数字符串在**调用前**是否已被填充——

这一点可以直接在 `0x511912`（调用点）断下、读出 8 个参数字符串来确认。
