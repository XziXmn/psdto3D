## 1. 这张表和工程文件的对应关系

工程 498 行。行 1–8 是头，行 9–40 是 32 个每层整数，行 41–72 是 `角度 分组 缩放`。

行 9–40 的值：层 4、5、6、7、10 为 -5，其余为 0。
界面层号 = 33 − 文件层号：

```
文件层 10 → 界面 23
文件层  7 → 界面 26
文件层  6 → 界面 27
文件层  5 → 界面 28
文件层  4 → 界面 29
```

和带狗原版逐格一致。工程文件本身没有问题。

写入点在装载器 `0x511408`：

```
00511A03  mov eax, [ebp-0x60]        ; 循环次数，来自 0x4D2F14 的输出缓冲
00511A60  mov ecx, [ebp-0x54]        ; = [0x52315C]，层数 32
00511A63  sub ecx, ebx               ; 33-文件层号 → 界面层号
00511A65  mov eax, [ebp-4]
00511A68  mov eax, [eax+0x30c]       ; 表格控件
00511A6E  mov edx, 2                 ; 第 2 列 = Offset
00511A73  call 0x48D628              ; 写单元格
```

Offset 和 cm 有各自的写入过程。带狗原版在这个工程上显示 `-5` 和 `-0.04`，这两个显示值不足以确定程序的通用换算公式。后续采样见[导入复盘与下一次对照](#导入复盘与下一次对照)。

## 3. 无狗版错在哪

> 下面这段把原因归到 `0x4E32FC` 不提交，已被第 4 节的实测取代。真正要改的是循环次数，见第 4 节。

无狗导入后，Offset 列留着 inf 的默认阶梯（-182、-137、-91、-46、+55 这些），还多出原版没有的 `h`。工程里的 -5 没有写进去。

写入循环本身没有狗判断。狗卡在它的**上游**：循环次数来自 `0x4D2F14`，而 `0x4D2F14` 要把狗缓冲区交出去解析，解析成功才把结果拷出来。

```
0x511A03  读 [ebp-0x60]，按这个次数写 Offset 列
    ↑
0x4D2F14  解析工程头，成功才把字段拷到各个输出（含 [ebp-0x60]）
    0x4D30E0  push 0x521008          ; 狗缓冲区
    0x4D30F7  call 0x4E32FC
    返回值必须是 0、-43 或 -67，否则跳到 0x4D31A0，50 字节的字段拷贝全部跳过
        ↑
0x4E334A  cmp dword ptr [0x51A72C], 0
          为 0 就走失败分支
```

`[0x51A72C]` 只有初始化成功才被写成 1（`0x4D713C`）。失败时返回 `0xFFFFFBBB`（-1109），这个标志保持 0。

同一块缓冲区上的授权检查：

```
0x4D2ADC  mov esi, 0x521008
          mov edx, 0x105             ; 261 字节
          call 0x4DDEA4              ; 用 cmyk3d_Ini.enc.lll
0x4DDEA4  从 0x51C9D5 拷 0x41 个 dword（文件里这 260 字节全是 0，运行时才被狗填上）
          再看 [0x51A72C]
```

所以无狗时不是“工程读错了”，是 **`0x521008` / `[0x51A72C]` 不满足，`0x4E32FC` 拒绝提交解析结果，Offset 列保持 inf 默认值**。这和错误截图一致：数字是默认阶梯，标记位是乱的。

`[ebp-0x48]` 那条 cm 比例（`[0x5230D0]` 与 1500 比较）是另一件事，不解释这张错误表。

- 读文件成功 → `0x4E33F7` 把这二十多个输出指针压栈，交给 `0x4E2054`，返回它的结果；
- 读文件失败且 `[0x51A72C]=0` → `0x4E33DF`，直接返回状态字。

实测返回的 -51 就是 `0x4E2054` 的返回值（[调用点](../_work/_4e34.txt)：`0x4E3464 call 0x4E2054`，`0x4E3469` 存进 `[ebp-0x20]`，`0x4E347B` 原样带回）。读数任务本身是成功的，卡在解密/校验这一步。


### 之前几轮为什么越修越偏

`cmykdrop\iatpatch.c:191` 的 `SANITIZE` 默认开启，会把记录表的 `+0x2C` 全部清零。上一轮日志里写得很清楚：

```
ENTER #1 … cnt=32 rec=0312F5EC … max2C=85 nz=22 dirty=1
SANITIZE 清 +2C x32（原 max2C=85 nz=22）
```

`+0x2C` 是层状态位，程序自己写过 22 个非零值（最大 `0x85`）。被这个 DLL 抹掉之后，界面上看到的标记当然不是程序的结果。同一个文件里还有 `GROUP_FIX`，可以直接改分组；`FILL_PROJ` 可以直接按工程填记录表。这些都是伪造，测出来的不是程序行为。

把 `SANITIZE=0` 关掉再跑同一步，程序在 `0x50A001` 崩（`C0000005`，`eax=0`，`ebp=7`）。也就是说「清 `+0x2C`」一直在掩盖渲染解引用空槽这个副作用；`_work\2022` 里那三段守卫（`0x509FF9`、`0x501080`、`0x5023B4`）遮的也是同一个东西。

结论：`_work\2022` 那一套逐列补丁全部停用，它们是在绕开被拒的解析器，不是在去狗。

### -51 的位置：`0x521008` 那块数据不可用

所以 -51 不是校验不通过，是**建流时拿到的数据不可用**。

而这份数据从来没被准备过：

| 观测 | 结果 |
|---|---|
| `0x521008` 运行时内容 | `0D F0 AD BA …`（Delphi 未初始化内存），见 `_dogbuf.bin` |
| 它的来源 `0x51C9D5` | 文件里 260 字节**全零** |
| `0x51C9D5` 硬件写断点（启动 + 菜单 7 + 菜单 10） | 命中 **0** 次（[日志](../_work/2022d/_key.txt)） |
| `[0x51A72C]` 硬件写断点 | 命中 **0** 次（[日志](../_work/2022d/_flag.txt)） |

`0x4DDEA4` 就是准备这份块的例程，它按标志分流：

```
004DDEAC  mov esi, 0x51c9d5 ; ecx = 0x41
004DDEC1  rep movsd                       ; 先把 260 字节搬到栈
004DDECE  cmp dword ptr [0x51a72c], 0
004DDED5  je 0x4ddf51                     ; 标志为 0 → 跳过狗解密
```

标志为 0，这段就整段跳过，`0x521008` 保持未初始化。加上前面查到的「没有任何指令写这个标志、唯一写入点是死代码」，结论是：**在这个环境里，狗那条取证路径整段是哑的**。Group / cm 之所以一直是空的，根子在授权块根本没有内容，跟哪一列怎么显示无关。

### 把标志置 1 之后：进入真正的狗例程

副本 `_work\2022e\` 只改一处：文件里 `0x51A72C` 的初值写成 1（md5 `0a9ac6b9…`）。其余与 `_work\2022d` 相同。

结果（[日志](../_work/2022e/_flag1.txt)）：

- `0x4DDEA4` 被调用，标志读到 1，`je 0x4DDF51` 这次不跳，狗解密分支真的执行；
- 走到 `0x4DDF0C call 0x4D726C`（狗接口例程）后崩：`C0000005 @ 7726A1C6`，`eax=0`，链 `0x4D728E ← 0x4DDF11 ← 0x503014`。

也就是说：门控一旦打开，程序就调用真正的狗接口，而仿真没给它准备好数据，它在系统模块里解引用空指针。

`0x4D726C` 的第一件事是 `EnterCriticalSection(0x521310)`（`0x4D7289 → 0x407660 → jmp [0x5243B0]`）。那个临界区本该由 `0x4D6FF0` 里的 `InitializeCriticalSection` 建好，而 `0x4D6FF0` 没有任何可到达的调用点。所以崩溃位置不等于问题所在：**真正缺的是那次初始化**。

### 狗到底是什么：一个 TCP 门，不做运算

`0x4D726C` 全文（[反汇编](../_work/_4d72b.txt)、[成功分支](../_work/_4d733.txt)）：

```
004D7279  mov [ebp-4], eax        ; src
004D7275  mov [ebp-6], dx         ; 命令字（word）
004D7272  mov [ebp-0xc], ecx      ; dest
004D727C  …
004D7284  push 0x521310 ; EnterCriticalSection   ← 崩溃点在这里
004D72AF  call send(sock, src, len, 0)           ; 发命令
004D72F3  call recv(sock, tmp, 2, 0)             ; 收长度
004D7349  cmp ax, [ebp-6]                        ; 长度校验
004D7374  call send(sock, src, len, 0)
004D73BA  call recv(sock, dest, 0x106, 0)        ; 收 262 字节块
```

`0x5212E0` 是 socket，`0x521310` 是临界区。**整条链只有发包、收包、长度比对，没有让狗算任何东西** —— 收回来的是固定的一块 262 字节数据。

这个结论决定做法：那块数据对同一个命令是固定的，可以像 SCSI 那批一样离线重放（`cmykdrop\dongle_mem.h`、`dongle_blobs.h` 里已经是按地址/按命令记录的块）。所以仿真 `0x4D726C` 就够了，不需要复现狗的运算。

之前「标志置 1 就崩」也解释清了：崩在 `EnterCriticalSection(0x521310)`，因为负责建这个临界区和开 socket 的 `0x4D6FF0` 没跑过。仿真时必须自己先把这两样备好。

`0x4ED130`（[反汇编](../_work/_4ed130.txt)）开头就是：

```
004ED13F  mov eax, [ebp - 8]
004ED142  cmp byte ptr [eax + 5], 0x3a     ; 第 6 个字符是不是 ':'
004ED146  jne 0x4ed1af                      ; 不是 → 当文件路径打开
004ED16D  call 0x407638                     ; CreateFileA(name, GENERIC_READ, …)
```

它是「按 URL 或按文件取资源」的通用函数：名字第 6 位是 `:` 就当 URL，否则当文件路径去 `CreateFileA`。传进来的 `edx` 实测是 `0x521008`，而那块 261 字节是未初始化垃圾，于是 `CreateFileA` 失败 → `-1` → `-51`。

### 这一版回显 DLL 的实测结果（cmykdrop\cmyktiff2_echo.dll）

### 回显是对的，错在参数型应答

把仿真实际返回的 501 字节也落盘（`_work\echo\_resp_echo_00..03_501.bin`），与真狗那五份逐字节比：

| 仿真 | 与真狗最近的一份 | 差异 | 结论 |
|---|---|---|---|
| `echo#0` | `real#0` | 124 B | 头 16 字节一致，之后是**本轮程序自己写的块**（`36000000` vs 上一轮的 `37000000`），差在运行时指针，属于正常 |
| `echo#2` | `real#2` | 408 B | 同上 |
| `echo#3` | `real#3` | 82 B | **参数型固定块取错了** |

回显型（`7B×16 + 写入块[16:] + FB`）本身是对的——两份记录分属不同进程，块里那些指针天然不同。真正的问题在**参数型**：程序发的短命令（应答以 `c8 00 00 00 …`、`02 00 00 00 …` 开头的那两条）应当返回固定数据块，仿真从 `K_DATA_BLOBS` 里按命令键挑，挑错了，于是层数被算成 123（`0x7B`）。

改为按句柄保存写入块（`blk_slot()`）后重跑，`[ebp-0x54]` 仍是 123，验证了这一点：不是回显取错块，是固定块映射错。

### 原样重放试过了，不行

把四份录制按命令键做成 `cmykdrop\echo_blobs.h`（键取命令标签的小端 dword：`000010FA`→`0xFA100000` 等），在读分支命中就直接 `memcpy` 那 501 字节。实测：

- 命中生效（日志 `replay blob FA100000` 两次）；
- 但 `0x4D30FC` **一次都没命中**——工程导入根本没走到解析。

原因很明确：那 501 字节里含**上一轮进程的运行时指针**（`37000000` vs 本轮 `36000000`），原样灌回去等于把别的进程的地址塞给程序。

所以结论定下来：

| 类型 | 做法 |
|---|---|
| 回显型（`7B×16 + 写入块[16:] + FB`） | 必须用**本轮**程序自己写的块合成，不能重放录制 |
| 参数型固定块（`c8…`、`02…`） | 是纯数据，可以重放，但要按命令键正确映射 |

### -50 是怎么算出来的（已定位到公式）

REA 拿到 `0x4E2054` 的完整伪代码（`_work/rea_4E2054_full.c`），`-50` 的来源是这几行：

```c
local_24 = FUN_004ed130(...);            // 打开设备
if (local_24 == INVALID) { … }
else {
  WaitForSingleObject(...);
  local_30 = FUN_004e089c(...);
  if (local_30 == 0) {
    local_2c = FUN_004e1b1c(local_8, local_c, (char *)&local_25, …);   // ← 状态字节
    local_30 = FUN_004df330(...);
    …
    if ((local_2c == 0) && (local_25 != 0xd5)) {
      local_30 = (uint)local_25;
      if (local_30 != 0) local_30 -= 0x100;      // 0xCE - 0x100 = -50
    }
  }
}
```

所以 **`-50` 就等于 `local_25` 那个状态字节减 0x100**：本环境取到 `0xCE`，真狗是 `0x00`（为 0 时不减，直接成功返回 0）。

`local_25` 由 `FUN_004e1b1c`（`0x4E1B1C`）写出。它的状态机里认这些标记：

```
*local_10  != -0x7d / -0x7c   (0x83 / 0x84)
*local_10  != -0x7b / -0x7a   (0x85 / 0x86)
*local_10  != -0x7e           (0x82)
```

也就是说，这是设备应答里的一段**带标记的协议流**，不是单个字段比较。我们的应答在这套标记上走岔了，最终落到 `0xCE`。

### 结论与下一步

最新一轮的实测数据：仿真里设备打开 **6 次全部被钩子接住**，但 `len=42` 的写入 **0 次**——真狗那边这一次是 `写 496 → 写 42 → 写 10 → 读 501`。也就是说不是钩子漏了，是 `0x4E089C` 自己没发那两步。

`0x4E089C`（会话执行者）的伪代码开头能看到它在拼 CDB：

```c
local_238[0] = -0x5b;   /* 0xA5 */
local_232 = 0x80; local_231 = 0x17;
local_236 = 0x1f0; local_234 = 0;
```

REA 内联只回了这个片段（64 行），后面全是 `FUN_004d21e8` 填充。要看清它按什么条件决定「写不写那段 42 字节载荷」，需要它的完整伪代码（`--full-output` 的保留证据），或者直接断在它的设备读写调用上，把 CDB 和载荷抓出来。

下一步就做这一件事：抓 `0x4E089C` 内部的 CDB 序列，与真狗那一段逐条对照。

### 关于「狗参与计算」这个说法（更正）

之前写成「设备改写/返回真实数据」，容易被读成狗在算。实测支持的结论恰恰相反：

- 程序只做三件事：写一块、读状态、读一块。没有下发任何「求值」请求；
- 应答里与写入不同的那几个位置（偏移 4–6、12–14、48 起）在**两次独立录制里数值完全相同**（`_resp_03` 两次都是 `02 04`、`A4 08`），说明它们是设备**自带的固定内容**，不是根据写入算出来的；
- `dongle\phys1.bin`（1,049,088 B，md5 `b88c8724a828bc49a72fa6cd60aa0013`，正是这只 U 盘的裸镜像）里**搜不到**这些字节（`02040000`、`A4080000`、`13003C00` 全部无命中），所以它们也不是存在盘上的数据，而是固件里的应答表。

结论：这只狗不参与运算，也不从盘上读业务数据；它只是在固定的偏移上返回自己的常量。之前「设备算出来」的措辞作废。

### 与 `LenticularOmega\vikey` 不是同一类

### 又一层：会话 4 的写入块本身就不同

把仿真里程序实际写出的 496 字节块也落盘（`_work\echo\_ew_*.bin`），与真狗那两份对比：

| 会话 | 差异字节 | 说明 |
|---|---|---|
| 3（`_ew_10` 对 `_w_06`） | 40 | 大部分是运行时指针（偏移 126–129、138…） |
| 4（`_ew_13` 对 `_w_08`） | 37 | 除指针外，**偏移 182、183 真狗是 `39 33`，仿真是 `00 00`** |

也就是说会话 4 的块里，程序本该填进去的两个字节在仿真里是空的——它是被前面几轮应答的内容带出来的。差异是**级联**的：会话 1/2 的细小差别传到会话 3，再传到会话 4，最后 `0x4E089C` 判定不发载荷、返回 -50。

### 这意味着什么

单点对齐（只修 501 应答、只修命令键）不够。要让它自洽，必须让**整条会话链**从第一轮起就与真狗一致，包括程序自己写进去的那些指针区域——而指针每轮运行都不同，靠录制回放无法逐字节吻合。

可行的收口办法只有两条：

1. **让程序自己算**：既然狗不参与运算，把设备那侧要返回的「数据区」按协议规则自己算出来（现在已知：应答 = 本轮写入 + 62（会话 3）/23（会话 4）个被设备改写的字节）。难点是这 62/23 个字节里有一部分与写入内容相关，需要从多组录制里反推规则；
2. **对照 99 版**：99 版把同一批数值写成常量，直接把它那几处常量拿过来，替换掉 2022 里「等狗算」的部分。这条不依赖会话自洽，最稳。

推荐走第 2 条：`docs/任务.md` 里本来就写着「对照 99 版，看它怎样在没有狗的情况下把参数写进图层表」。

### 更正：USB/IP 通道是支持 SCSI 直通的

上一版这里写过「USB/IP 不搬厂商 SCSI 直通」，**那是错的**，错在我的探针：

- 探针原来用 `#pragma pack(1)` 手写 `SCSI_PASS_THROUGH`。x64 下 `DataBufferOffset` 有 8 字节对齐，
  紧凑打包把它放到偏移 20（正确应为 24），于是 `DeviceIoControl` 一直报 1306/87。
- 改正后（去掉打包、`Length = sizeof(SPT)`，并改用 `SCSI_PASS_THROUGH_DIRECT`），
  对虚拟磁盘 `READ CAPACITY` 立刻正常返回，说明探针本身没问题。

对 usbip 挂载的狗实测（`3&1FF4DFBE&0`）：

```
READ CAPACITY  -> ok  cap=00000800 00000200   (2049 × 512 = 1,049,088，正是这只狗的大小)
厂商写 0xDD 496B -> ok
厂商读 0xD1 5B   -> err=121 (信号灯超时)
之后所有请求      -> err=1167 (设备未连接)
```

结论修正为：**通道能跑 SCSI 直通，设备也认得**。读超时是内容问题——第一次喂的是全零块，
固件可能因此挂起并掉线；应当先用真狗录到的那块输入。

### cm 列的公式与真正的缺口（静态读出来的）

`0x513A30` 里 cm 的算法（`0x513B6A`–`0x513BD2`）：

```
A = 控件值            (0x513B4B  call 0x45fa84 读出，[ebp-0x14])
B = 表格第 2 列文本   (0x513B65  call 0x48d5b8 读出，[ebp-4])
cm = round( (B - A) * 100.0 * [0x5232F4] / 10000.0 ) / 100.0
```

其中 `[0x5232F4]` 是 **int64**，在同一函数的 `0x513AEE` 处由下式算出：

```
[0x5232F4] = [0x523190] * <栈上的系数>     (fild [0x523190] / fmulp / fistp [0x5232F4])
```

函数入口还有个提前返回判断（`0x513A61`）：`[0x5231A8]` 或 `[0x5231B0]` 为 0 就整段跳过。

运行时读到的实际值（无狗、走仿真，`_work\echo\_runN.txt`）：

```
CMIN g1=[0x5231A8]=3000000   g2=[0x5231B0]=1500000   g3=[0x523190]=0   g4=[0x5232F4]=0
```

- 门控两个都非零，**没有**提前返回；
- 真正的零是 `g3=[0x523190]`，于是 `g4=0`，`cm = round(...×0/10000)/100 = 0`。

也就是说 cm 全零的链路是：解析没提交 → `[0x523190]` 没被填 → `[0x5232F4]`=0 → cm 恒为 0。
这跟「Group 显示不对」「Offset 只写一行」是同一个根因，不是三件事。

结论：在拿到设备之前，cm 这条线无法再往前推——缺的就是解析要填的那一个（或几个）全局量。

### 装载器里那次 cm 调用在 SEH 处理器里（重要）

线性扫描 `0x511408` 起的装载器（`_work\_ldr4.txt`）：

```
005125CC  xor eax, eax
005125D4  push 0x512610        ← 注册异常处理器
005125D9  lea eax, [ebp-0x2a4] ; call ...
005125EE  mov edx, [0x523230]  ; 曲线数组
005125F4  mov ecx, [0x523104]  ; 下标
005125FA  mov edx, [edx+ecx*4] ; ← 下标越界就在这里 AV
00512608  ret                  ← 正常路径在这里返回
00512610  push 0x512774        ← 处理器开始
...
0051266C  call 0x513A30        ← cm 就在这里被调用
00512671  ...
```

也就是说：**参考运行里 cm 的五个 -0.04，是被 `0x5125FA` 的下标越界异常带到处理器里算出来的**，不是正常路径。

对照：参考运行的帧链 `frame[0] ret=00512671` 确实存在（64 次），而我们的仿真运行里这条 `ret=00512671` 一次都没有。

### 试过的两个强制手段（都没成）

| 手段 | 做法 | 结果 |
|---|---|---|
| 改 `[0x523190]`（g3） | DLL 线程写 1000000 | G 仍为 0，cm 仍全 0——函数每次进入都用 g3 重算 g4，但该路径没走到 |
| 制造同样越界 | DLL 写 `[0x523104]`=0x7FFFFFFF | 触发的是 `Invalid numeric input`，`ret=00512671` 依旧没出现 |

原因：`[0x523104]` 是曲线循环的活下标，提前改大后循环先崩，走不到 `0x5125FA`。

### 设备被写挂的恢复步骤（宿主机侧）

## 真狗 SPT 包头（2026-11-20 抓到）

程序在 `_work\real3` 里跑出 `_dongle.log`，每对 `SPT` 行就是一个 44 字节
`SCSI_PASS_THROUGH`。按结构解出来：

```
偏移 0  Length            = 0x2C (44)
偏移 4  TargetId          = 1        ← 之前探针填的是 0
偏移 6  CdbLength         = 0x10     ← 16，不是常见的 10/12
偏移 8  DataIn            = 0 写 / 1 读
偏移 12 DataTransferLength = 数据长度
偏移 16 TimeOutValue      = 100
偏移 24 SenseInfoOffset   = 0x30 (48)
偏移 28 CDB[16]
```

CDB 实例（524 那一轮）：

| 用途 | CDB |
|---|---|
| 写 496 @0 | `DD FE F0 01 00 00 80 17 00 00 00 00 00 00 00 00` |
| 写 26 @0 | `DD FE 1A 00 00 00 80 09 00 00 00 00 20 4E 00 00` |
| 写 10 @0x1F0 | `DD FE 0A 00 F0 01 80 16 00 00 00 00 00 00 00 00` |
| 写 0 @4 | `DD FE 00 00 04 00 80 28 00 00 00 00 00 00 00 00` |

要点：

1. **`CDB[1] = 0xFE`** —— 探针之前填 0，这是写挂设备的最可能原因；
2. `CDB[2..3]` = 长度，`CDB[4..5]` = 槽位地址，和之前的判断一致；
3. `CDB[6..7]` 每次都不同（`0x1780`、`0x0980`、`0x1680`、`0x2880`，都是 128 的倍数），
   形态像指针低位派生值，与长度没有简单关系；
4. 26 字节那条在 `CDB[12..13]` 还有 `0x4E20`（=20000）。

记录器已改成**读写两侧都 dump 包头**（之前只 dump 写），下次跑一遍就能把读方向的 CDB 也拿到。

| 8 | `DD 496 @0` | `D1 496 @0` | 5 |
| 9 | **`DD 42 @0`** | `D1 42 @0` | 5 |
| 10 | `DD 10 @0x1F0` | `D1 10 @0x1F0` | 501 |

第 9 组就是一直卡住我们的会话 4（42 字节，`opensaveset.enc.lll`）。

另一个新事实：10 字节命令的内容**每次运行都不一样**——
11:21 这次是 `8F 00 05 00 00 00 00 00 00 00`，更早一次是 `00 00 10 FA 1A 00 CE 5D 26 77`。
所以「按录制顺序原样回放应答」这条路不可靠：命令本身随运行变化，设备是拿命令去查自己的表。

这也解释了为什么用户态仿真总在会话 4 卡住：我们按固定表应答，而真实设备是按**当次命令**应答的。
