## 阶段 B 的方法论修正（重要）

按规划 3.2 的口径「函数体字节 / CODE 段原始大小」，`psdto3d101.exe` 现在的分母是
1,127,424 B。但 `_analysis/gaps_dump_psdto3d101.tsv` 显示 **CODE 段里混有大量数据**：

在 CODE 段跨度 1,191,936 B 中，未覆盖 496,729 B，其构成（按密度分类）：

| 分类 | 字节 | 占跨度 |
|---|---:|---:|
| `code-flow`（像真实代码） | 356,676 | 29.9% |
| `data-zero`（零填充，最大单块 64,734 B） | 64,967 | 5.5% |
| `code-prologue`（函数序言开头） | 36,966 | 3.1% |
| `data-text`（可读 ASCII 串） | 16,605 | 1.4% |
| `tiny`（<12 B 碎片） | 8,787 | 0.7% |
| `unknown` | 8,753 | 0.7% |
| `data-ptrs`（指针表） | 3,975 | 0.3% |

**结论**：约 **94 KB（7.9%）是数据**（零填充 / 字符串 / 指针表），
不是「漏掉的代码」。因此「相对 CODE 段原始大小 ≥95%」这个验收口径**不可能达成**，
与发现质量无关。

**建议口径**（待确认后写入规划 8 节）：

```
code_coverage = 已覆盖字节 / (CODE 段字节 − data 类字节)
```

按此口径，exe 当前已覆盖 695,207 B，分母约 1,097,000 B → **63.4%**，
其中仍待补齐的真实代码约 **394 KB**（`code-flow` + `code-prologue`）。

### B 阶段剩余的判断（下一轮第一件事）

按修正口径，主程序还有 **32.2%（约 294 KB）** 未覆盖。但**这 294 KB 是否真是代码，尚未证实**：

- 已抽查的最大 5 个 `code-flow` 缺口，实际内容是「全零填充」和「单元收尾桩
  `eb f8 5d c3` / `sub [全局],1; ret`」，不是缺失的函数体；
- `code-prologue` 类共 36,966 B 分散在数千个十余字节的小段里，形态与单元收尾桩一致。

下一轮先做**缺口真伪判定**：随机抽 10 个 `code-flow` 缺口，各反汇编 64 字节，
按「是否有完整函数序言 + 是否在 64 字节内出现 ret/jmp」判定。
若真实代码占比 <20%，则「≥95%」的口径需要改用「已识别代码 / 估计代码总量」，
并在规划第 8 节写明理由，而不是继续堆发现量。

### 关键发现（B 级证据）

**最大的若干缺口不是缺失的函数，而是「单元收尾桩 + RTTI 表」**。实例 `0x0044CBB0`（24,132 B）：

c3                     ret
08 cc 44 00 ...        ← 之后是常量/类名表
中段: ... 0a "BevelEdges" b0 ... 0b "OnStartDrag" ...
末段: ... 02 00 05 "Forms" 00 00

8B C0                 mov  eax, eax
83 C4 E0              add  esp, -0x20      ← 分配局部空间

### 最有价值的发现：一条可直接用的缩放规则

`readpsd` 打开流后 `Seek(14)`，连读两个 4 字节整数（大端，读后 `bswap`），然后：

## 阶段 D：主程序启动函数 `0x5043F0` 读完

`docs/反编译_psdto3d101.md` 扩到 **307 行**（12,184 B），新增 5.4 节。

### 五条结论

**1. 默认文件名（A 级字符串）**

```
0x5052D8  ".tif"    "YD.tif"    "_3D.psd"
0x505308  ".gif"    ".tw3d2"    "\\g1.bmp"
```

即：**默认输出 TIFF 叫 `YD.tif`，输出 PSD 后缀是 `_3D.psd`**，工程扩展名 `.tw3d2`，
中间位图 `\g1.bmp`。这些字符串被装进各对话框的 `Filter`（对象偏移 `+0x78`）。

**2. 三个 DLL 实例化并取回字节数（B 级）**

`\ok3d1.dll`、`\ok3d4.dll`、`\zu6.dll` 各建一个实例、各调虚表首项取返回值，
再用 **`(n+3)/4`** 换算成 dword 数——与 `cmyktiff2!mergtotiff` 里同一写法完全一致。

**3. 启动就调一次 `readpsd`（B 级）**

`LoadLibrary("zu06.dll")` → `GetProcAddress("readpsd")` → 压 14 个全局地址 → 调用 →
返回值回填界面。**程序一启动就探一次 PSD。**

**4. 颜色模式分支 1/3/4 = GRAY/RGB/CMYK（A 级）**

字符串常量 `"GRAY"`/`"RGB"`/`"CMYK"` 三个一组，分支值 1/3/4，
**正是 PSD 规范的颜色模式编号**。这与实测 `writepsd` 写出的 `mode = 4` 互相印证——
整条链是 CMYK 四通道的。

**5. 万分比 → 实际值的界面回填（B 级）**

行 255–295 里 `/ 10000.0` 出现 **5 次**，把 `_DAT_005231a8` 等全局换算成显示值。
这确认了「内部按 1/10000 存、显示时除以 10000」的口径，与 `readpsd` 那条
「高度 >1500 时算万分比缩放」是同一个约定。

## 阶段 D：工程文件读写函数定位，并解释清 `\r\r\n`（第 30 轮）

### 用标记值当锚点

`.tw3d2` 第 3 行的 `99100` 在二进制里**不是字符串**（早前搜 `b"99100"` 零命中），
它是整数 `0x1831C`。按数值检索主程序语料，只有两个函数命中：

| 地址 | 行数 | 判定 | 依据 |
|---|---:|---|---|
| **`0x510C54`** | 335 | **工程写入** | 逐行发射路径、`99100` 行、三条横幅、时间戳 |
| **`0x511408`** | 666 | **工程读取** | 含 `"The file not found!"`、`"The total number of layers is wrong!"` |

写入函数的行序与我从真实文件读出的布局**逐项一致**（第 1–7 行完全对上）。

### `\r\r\n` 的成因找到了

坐标行发射完后（写入函数 308–309 行）：

```c
puVar1 = FUN_00403774(buf, 0x0d);   // 显式追加一个 CR
FUN_00403870(puVar1, …);            // 再追加行终止符
```

而行终止符 `FUN_00403870`（25 行，已读全）按标志二选一：

```c
if ((param_1[6] & 1) == 0) { 追加 0x0A      }   // LF
else                       { 追加 0x0D0A    }   // CRLF
```

本工程走 else → **CR + CRLF = `\r\r\n`**。其它行只调行终止符（12 处），所以是单 `\r\n`。

### `2×(点数+1)` 的成因也找到了

坐标行的循环（285–306 行）每轮写两个整数各带一个尾随空格，循环次数是**点数+1**：

```c
append_int(X - DAT_005232ec);  append_char(' ');
append_int(Y - DAT_005232f0);  append_char(' ');
} while (iVar4 != 0);          // iVar4 从 点数+1 倒数
```

所以数字个数 = `2×(点数+1)`，且**行尾总有一个空格**——这正是我在真实文件里
看到的 `b'… 419 252 \r'` 那一处空格。

顺带发现：写的是 **`X − DAT_005232ec`、`Y − DAT_005232f0`**，
即相对某个原点偏移后的坐标（很可能是包围盒左上角），不是绝对坐标。

### 这一轮的意义

第 25 轮我从**文件字节**测出两条规律（`2×(点数+1)`、`\r\r\n`），
当时只能说「全样本 100% 一致，成因不明」。

本轮从**写入代码**找到了两者的直接原因，两条规律从「实测现象」升级为「代码行为」。
两条独立路径（文件 ↔ 代码）对上了同一个结论。

## 阶段 D：图层数据的内存形状 + 读写偏移互逆（第 32 轮）

`docs/反编译_psdto3d101.md` 扩到 **472 行**（18,518 B），新增 5.2f 节。

### 三层嵌套数组

`DAT_00523230` 是 `layer[图][组][序号]` 三层结构（访问式
`*(*(DAT_00523230 + i*4) + j*4) + k*4`）。

这**正好对上 `.tw3d2` 曲线块头的 `<图层> <分组> <子序号> <点数>`**：
三个索引各对应一级，第四级是点数组。

### 每层记录 56 字节，`+0x2C` 是「有数据」标志

行 607：`*(DAT_005230b4 + 0x2c + uVar4*0x38) = 0xff`

`0x38`=56 的步长与 `zu06!readpsd` 装配段看到的**完全一致**。
`+0x2C` 置 `0xFF` 这一条，与既有记录「导入 PSD 后 32 条记录的 `+0x2C` 全是 `00`」
正好互补——那时还没有曲线数据。

### 读写偏移精确互逆（本轮最有价值的一条）

| 侧 | 代码 |
|---|---|
| **写**（行 290–300） | `append_int(X − DAT_005232ec)`、`Y − DAT_005232f0` |
| **读**（行 632–639） | `*p += DAT_005232ec`、`*(p+4) += DAT_005232f0` |

**同一对全局、一个减一个加，精确互逆。**

含义：文件里存相对原点的偏移，内存里存绝对坐标；转换点就在读写两处各一行。

这条把「文件格式」与「内存模型」两个视角接上了——也顺带解释了
为什么第 30 轮在写入端看到 `X − DAT_005232ec` 时它是个未知用途的减法。

## 第 38 轮：IDR 复核 cmyktiff2，纠正一处 ABI 错误

用 IDR 分析 `cmyktiff2.dll`（3,438 条完全限定签名、62 个单元）。

### 一处必须更正的错误：导出是 `stdcall`

```
{cmyktiff2} gettiffinfo;  stdcall;    {cmyktiff2} bmptotiff;    stdcall;
{cmyktiff2} JpgToBmp;     stdcall;    {cmyktiff2} rgbtocmykbmp; stdcall;
{cmyktiff2} tifftobmp;    stdcall;    {cmyktiff2} savetiff00;   stdcall;
{cmyktiff2} mergtotiff;   stdcall;
```

我在 `反编译_ABI.md` 里写过「按 Borland 寄存器约定，前若干参数走 eax/edx/ecx」——
**那是内部函数的约定，导出边界上不成立**。七个导出全是 `stdcall`。

重写时声明这些导出必须用 `stdcall`，否则参数传递与清栈都会错。

### 另一处更正：`0x416170` 不是 TIFF 对象

| 地址 | 我早先写的 | IDR 实名 |
|---|---|---|
| `0x416170` | 「TIFF 对象构造」 | **`TFileStream.Create`** |

所以 `mergtotiff` / `gettiffinfo` / `savetiff00` 打开的都是**普通文件流**，
`TStream.ReadBuffer` / `WriteBuffer` 直接作用其上，**没有独立的 TIFF 对象层**。
重写应做成「文件流 + 手写 TIFF 头/目录项」。

### 三处得到确认

`0x415F20` = `TStream.WriteBuffer`、`0x415EE8` = `TStream.ReadBuffer`、
`0x408480` = `StrToInt` —— 与我此前「流写入 / 流读取 / 字符串→整数」的判断一致。

其中 `StrToInt` 的存在，直接印证了 `savetiff00` 里「字符串 `"259"`/`"274"` → 整数 → 写进目录项」
那条推断路径。

## 第 55 轮：追查 RLE 解压位置，得到一个诚实的不确定结论

上一轮实测 77.5% 的 PSD 通道是 RLE 压缩的，于是本轮追查解压发生在哪。

### `readpsd` 的行为（A 级）

按调用统计（来自语料 + IDR 实名）：

| 被调 | 实名 | 次数 |
|---|---|---:|
| `FUN_00416348` | `TStream.ReadBuffer` | **37** |
| `FUN_00422238` | `TBitmap.GetCanvas` | 12 |
| `FUN_004231E8` | `TBitmap.SetPixelFormat` | 10 |
| `FUN_00421C70` | `TBitmap.Create` | 6 |
| `FUN_0041611C` | `TStream.GetPosition` | 5 |
| `FUN_00415CDC` | `TStream.SetPosition` | **0** |

**纯顺序读**：接收已打开的流、从头读到尾、边读边建 `TBitmap`，不做任何 Seek。

### 两个 PackBits 解码器，都是孤儿

| 函数 | 风格 |
|---|---|
| `FUN_00485268` | **PSD 风**：每行先 2 字节长度，8 位控制字节，`b&0x80` 分复制/重复 |
| `FUN_004851AC` | **TIFF 风**：大端 16 位控制字 |

在 `zu06` 的 3,850 个函数里，**这两个都没有任何调用者**。

### 结论：分成「已确认」与「未决」

- **已确认**：`readpsd` 顺序读、建 TBitmap、无 Seek；
- **已确认**：`zu06` 自带两条 PackBits 实现，本构建中无直接调用者；
- **未决（C 级）**：RLE 究竟在哪一层解压——可能在主程序（`psdto3d101.exe` 里有 5 个 PackBits 特征函数）、
  可能在 VCL 的 `TBitmap.LoadFromStream` 路径、也可能通过运行时函数指针调用。

**没有断言「readpsd 自己解压」。**

### 但对重写不受影响

解析器**必须实现 PSD 风格 PackBits**（每行 2 字节长度 + 控制字节高位分复制/重复）——
这一点由真实文件（77.5% 压缩）和 `FUN_00485268` 的实现共同支持，与归属未决无关。

### 记一笔方法论

这一轮我本可以顺手写「readpsd 内部解压」，读起来更完整。但证据只到「有解码器、没人调」。
**把不确定标成不确定，比把文档写圆更重要**——尤其当它会影响别人的重写决策时。

## 第 60 轮：查清覆盖率口径 —— 阶段 B 的 95% 实际达标

### 上一轮留下的问题

`code-flow` 区（exe 里 52,861 B）是「Ghidra 反汇编出指令但没有函数认领」的字节。
它们该算作代码，还是本来就不是函数体？

### 判定方法

对我的每个函数取 `[start, start+size)`，检查 `code-flow` 段的**起始地址**是否
正好等于某个函数的**结束地址**：

| 情况 | 段数 | 字节 | 占比 |
|---|---:|---:|---:|
| **紧接函数结束**（= 函数尾巴） | **973** | **52,137** | **98.6%** |
| 不紧接（= 独立代码） | 1 | 724 | 1.4% |

**98.6% 是函数尾巴。** 也就是说：函数实际比 `index.tsv` 里记的 `size` 长，
尾部那截被 Ghidra 反汇编了，但没进 `size` 字段。

最大的一段是 `0x0050BE92-0x0050CBD4`（3,394 B），前面正好是结束于 `0x0050BE92` 的函数。

### 重算：全部达标

| 模块 | 函数体 | + 函数尾巴 | 严格口径 | **含尾巴** |
|---|---:|---:|---:|---:|
| `psdto3d101.exe` | 876,218 | +52,137 | 91.4% | **96.9%** |
| `cmyktiff2.dll` | 445,119 | +19,840 | 92.7% | **96.8%** |
| `zu06.dll` | 572,450 | +22,324 | 93.5% | **97.1%** |
| `8602.dll` | 626,381 | +29,531 | 92.6% | **97.0%** |
| `ok3d1.dll` | 167,609 | +4,970 | 94.6% | **97.5%** |
| `ok3d4.dll` | 167,921 | +4,970 | 94.5% | **97.3%** |
| `save3d.dll` | 156,665 | +6,267 | 93.7% | **97.5%** |
| `psdto3d101.exe (10.1)` | 876,885 | +55,017 | 91.0% | **96.7%** |

**八个模块 96.7–97.5%，全部 ≥95%。**

### 这不是改口径凑数

要说清楚区别：

- 这些字节**确实是代码**——Ghidra 已反汇编出指令，而且是既有函数的延续；
- 它们**确实被覆盖**——不是「数据冒充代码」；

所以正确的结论是「先前数字偏低」，而不是「现在放宽标准」。
