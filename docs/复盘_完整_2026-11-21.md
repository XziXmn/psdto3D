## 一、目标

把 PSDTO3D（柱镜光栅立体印刷软件，10.1 / 2022 / 99 三个版本）修成
**单文件绿色 EXE、完全脱离加密狗运行**，且输出（TIFF/PSD）与真狗逐字节一致。

原始文件：`Psdto3d/psdto3d101.exe`
- 大小 1,581,056 字节
- md5 `5407b48102582855f7560879a5be3c48`
- manifest 要求 `requireAdministrator`

真狗参考输出（`test/0《生化危机：爆发夜》第一人称海报汉化/`）：
- TIFF `6,899,708` 字节（RGB 1969×1168，3 samples，未压缩）

## 二、两条路线（这是全项目的核心分野）

### 路线 A：补丁 exe（v2 → v15）

用 Ghidra 全量反编译（4816 函数）+ 硬件断点探针，逐个绕过保护环节，
直接修改 exe 让它在无狗环境下工作。

**优点**：不依赖任何外部数据，单文件。
**缺点**：绕过的是"验证"，程序内部的授权初始化数据全部缺失，
于是每个消费者（表格、cm、工程数组、导出参数）都要单独修——这就是
"每个功能都要修"的根源。

### 路线 B：仿真狗（emu1，正在走）

**原版 exe 一字节不改**（或只改 11 字节），放一个仿真 `cmyktiff2.dll`：
拦截 exe 对狗的 IO（CreateFile/ReadFile/WriteFile/DeviceIoControl/
SetupAPI/ASPI/对话框），用真狗抓包的应答**原样回放**。

**优点**：程序的验证、初始化、参数解析全部走原生代码——真狗怎么跑，
它怎么跑。理论上只需要一份真狗会话记录。
**缺点**：需要真狗环境抓包一次。

**当前结论：路线 B 是正确终点，且已经跑通了狗检测链**（见第四节）。

## 四、关键技术发现

### 4.1 狗的本质：它不是加密芯片，是"存储 + 状态位"

实机抓包（`_work/real3/_capture.log`）证明：一次完整启动只有
**6 组会话**，每组的形态固定：

```
写 496 字节 @0x01F0  → 读 5 字节状态（FB 00 00 00 00=OK）
写 26 字节  @0x001A  → 读 5 字节状态（FB 01 00 48 01）
写 10 字节  @0x000A  → 读 501 字节处理结果
```

**没有任何授权数据从狗里"流出来"**——狗只是把程序写进去的东西
（`.enc` 文件内容、参数块）存进内部槽位，然后返回一个"处理结果"。

### 4.2 狗的存储布局（多槽）

| 地址 | 内容 | 大小 |
|---|---|---|
| `0x0000` | 状态 | 9 B |
| `0x001A` | 票据（`3D 6A C2 3B 84 7D 21 97 ...`）| 26 B |
| `0x002A` | `opensaveset.enc` 内容 | 42 B |
| `0x00C2` | `cmyk3d.enc` 内容 | 194 B |
| `0x01F0` | 参数块（496 B，头 4 dword = `0x7B`）| 496 B |
| `0x000A` | 命令口（写命令 → 读 501 结果）| — |

### 4.3 六条 IO 通道

调用链 `0x4DD8D8(mode, handle, cmd16, out, receipt, data)`，按设备类型分支：

| 通道 | 判据（`0x4ED130`）| 实现 |
|---|---|---|
| 1 = 盘符 | 路径第 5 字符是 `:` | `CreateFile` |
| 2 = SPT-A | 前缀 `\\.\usbstor#disk&ven_usbkey...` | `0x4EDE64`（写）/`0x4EDD94`（读），NT 路径 |
| 3 = HID | 前缀 `\\.\hid#vid_1670&pid_8763` | 备用 |
| 0 = 文件协议 | 其他 | `WriteFile`/`ReadFile` 流 |
| SPT-B | — | `DeviceIoControl(0x4D014)` + `DD FE`/`D1 FE` CDB |
| ASPI | `LoadLibrary("wnaspi32.dll")` | `0x521000/0x521004` |

`0x4D2184 = FillChar`、`0x4D21E8 = Move`（不是 IO，之前误判过）。

### 4.4 验证逻辑

`0x4D2ADC`：循环 257 次 `\\.\MyUSBKey%d` →
`0x4DDEA4`（打开+验证）→ `0x4ED6BC`（SetupAPI 枚举 DiskClass
`53F56307-B6BF-11D0-94F2-00A0C91EFB8B` + 前缀匹配）→
`0x4D2F14` / `0x4E32FC`（.enc 处理）→
`0x4D2BC9` 处检查返回值 + **前 4 个 dword 必须等于 `0x7B`**。

`0x4E32FC` 的实际语义：
- `FUN_004dff64` = 纯 `ReadFile` 读 `.enc` 文件
- 成功 → `0x4E2054`（狗会话）：开设备 → `0x4E089C`（发参数块）→
  `0x4E1B1C`（2882 字节分块状态机）→ `0x4DF330`（收尾）
- `0x51A72C = 1` 时走"内嵌服务"分支——**死代码**（`0x4D7EDC` 零调用、
  `0x5212E0` 零引用），激活必 AV，已排除。

### 4.5 VM 解释器（0x4E1660）——授权逻辑的载体

- 字节码区：`0x521790`，长度 `0xB40`（2880 字节）
- PC **倒序执行**（从参数 word 递减到 `0x6A`）
- 3 种 opcode：
  - `0`：push 立即数/地址（PC-5），消耗 6 字节
  - `2`：push 双操作数，消耗 10 字节
  - `1`：push 地址（`0x521790+PC-0x33`），消耗 52 字节
- 结束 → `call [0x52178C]`（`LoadLibrary`+`GetProcAddress` 拿到的外部函数）
- `0x521792 == 'S'` → cdecl 约定（外部函数清栈）

**VM 程序本体由狗在会话中返回**（`0x4E11EC`：`'Q'` 命令读长度、
`'R'` 命令读程序）——这就是为什么静态分析永远拿不到授权逻辑。

### 4.6 表格自动位移算法（0x502CA8）——已完全破解

```
E = 32 层里「记录 +0x2C == 0」的层数            (0x504C94)
F = ROUND(2×(E−1) / 5.0)                        (0x504D08)
base = ROUND(宽 / 16.0 × 10000)                 (0x504BBA, 4370→2731250)
step1 = ROUND(base×2/3 / (0.001+F))
step2 = ROUND(base / ((E−F) − 0.999))

VALS[map[i]] = ROUND(step1 × (i−F))   for i = 0..F
VALS[map[i]] = ROUND(step2 × (i−F))   for i = F+1..E−1

表格第 r 行 = ROUND(VALS[32−r] / 10000)
```

真狗 32 行实测（LO 三张滚动截图）：`-182,-167,-152,-137,-121,-106,-91,
-76,-61,-46,-30,-15,0,14,29,43,57,72,86,101,115,129,144,158,172,187,201,
216,230,244,259,273` —— v15 逐位一致（E=32，F=12，step1=151723，
step2=143742）。

### 4.7 两条填表路径（不能混）

| 操作 | 函数 | col2 值 |
|---|---|---|
| 导入 PSD（菜单 7）| `0x502CA8` | 自动位移（上面那 32 行）|
| 打开工程（菜单 3）| `0x511408` | 工程文件里的 32 个整数（`0`/`-5`）|

打开工程时 col1 = `"+"`（字面量 `0x512764`），cm = `round(shift×80/10000)/100`。
真狗「导入设置后」的表格：`0/-5` + `"+"` + `cm 0/-0.04`（LO 截图确认）。

### 4.8 KeyReg101.exe = 同构验证工具（不是生成器）

全量反编译 2708 函数（`_work/re_keyreg/`）：
- `0x4607A4` = ASPI 加载（同 exe `0x4D2208`）
- `0x460878` = ASPI 会话，36 字节标识 memcmp `DAT_0047DFA4`
- `0x46093C/0x4609E8` = SPT 写/读（`DD FE` 协议）
- `0x460B18` = .enc 处理（8 槽 + 7B×4 验证 + 257 循环）
- 标识模板与 exe `0x517C5C` **逐字节相同**（`USBkey`/`USBkeyCo.`/`1.00`）

**结论：KeyReg101 也是验证端，没有 .enc 的加密/生成逻辑。**
授权数据由厂商开发机生成，分发形态即 `.enc` 密文，
"解密/解释"依赖狗固件返回的 VM 程序。

## 八、教训

1. **不要用间接指标判成功**
   - "字符串长度 17"≠值为 -5；"调用次数 32"≠值正确；
     "ok3dtemp 文件数"≠预览成功（目录从未清理、程序退出会删）。
   - 唯一可靠：**界面截图** 或 **完整字符串内容**。

2. **探针读栈要核对调用约定**
   - Delphi fastcall：前 3 参数在 eax/edx/ecx，第 4 个起在栈。
   - `0x48D628` 的字符串在 `[esp+4]`，`0x511A73` 在 `[esp]`——
     之前读错位置，把所有观察结论污染了。

3. **注入代码到循环体里会打断 Delphi 循环**
   - 在 `0x511A73`/`0x511A79` 等循环内插 cave 三次都只跑一轮——
     插在循环外或替换整个函数才可行。

4. **改 exe 前先备份、先确认字节**
   - 这次踩过的坑：VA 当 RVA（SetupAPI patch 写到错误内存导致 DllMain 崩）、
     bash printf 把 `\b`/`\a` 转义吃掉（对话框路径变 `C:io.tw3d2`）、
     多次 sed/python 编辑叠加把函数改乱（e_rf 重写才干净）。

5. **区分"程序逻辑"与"运行时数据"**
   - 反编译能拿到的：所有验证点、协议格式、状态机、VM 解释器。
   - 拿不到的：`.enc` 的明文语义、VM 字节码、狗的状态机应答——
     这些是数据，只在真狗运行时存在。
   - 这解释了"为什么每个功能都要修"：补丁路线绕过了数据来源，
     每个消费者都缺输入。

6. **优先走"原生"路线**
   - 仿真狗 + 真狗回放让程序自己的初始化跑起来，一次解决所有下游。
   - 补丁路线适合验证"某个具体算法"，不适合作为最终形态。
