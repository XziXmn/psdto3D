## 六、补充实验（round 1）：直接写第 3 列

按“绕开 cm、在 Offset 写入处同时写列 3”的思路建 `_work\v8`：

- 在 `0x511A73`（原 `call 0x48D628`）改为跳 cave（`0x4E0B00`，118 字节）；
- cave 内：先执行原 setter（写 Offset），再按 cm 的算法
  `round(raw×g4/100)/100` 算值、用 `0x40B134` 格式化、调 setter 写列 3，
  最后跳回 `0x511A78` 继续循环。

结果：

```
AV=0 ；列分布 col0:33 / col1:32 / col2:32 ；col3=0
cave 命中 1 次（t=80.03，ebx=0）
```

**关键现象**：cave 只被调用 1 次，而 Offset 循环本应 32 次（`0x511A73` 在 v2 上实测 32 次命中）。

### 第三次复现的同一现象

| 尝试 | 挂点 | cave 命中 | 结果 |
|---|---|---|---|
| 1 | `0x511A79`（循环尾） | 1 次 | 循环中断 |
| 2 | `0x511A36`（循环体内） | 未验证 | 无 col3 |
| 3 | `0x511A73`（循环体内，替换 setter 调用） | **1 次** | 循环中断 |

三次都是“插入循环体后，循环只跑第一轮”。**这不是挂钩点选错，而是插入行为本身
破坏了 Delphi 的异常/栈帧状态**，导致剩余迭代被展开跳过。

### 结论

- 在 `0x511408` 的 Offset 循环内部做任何代码注入都不可行（至少用这种 cave 方式不可行）；
- 要写第 3 列，必须选**循环之外**的位置，例如整个装载器返回之后；
- 而装载器返回点（`0x50A769`）已被验证会 AV（早前结论）。

### 因此下一步应改换策略

1. 不在导入流程内注入，改为**在程序启动后注册一个定时器/线程**，导入完成后由它补算 cm；
2. 或者直接改 `0x513A30`（cm）的入口：跳过它的两个门槛判定与网格读取，
   让它用别的数据源（例如 `[0x5230B4]` 数组）计算——这需要精确改写函数体，
   但属于“替换实现”，不涉及在别的函数里插代码。

## 七、round 2：存储路径排查

### 1. 容器是否存在（写断点处读取）

在 `0x511A68`（写入取网格对象处）同时读网格字段：

```
STORE grid=025D97C8 +2D8=025D9C6C +2DC=025D9C34
（32 次全部相同）
```

**结论**：`0x48D408` 已把行/列容器建好，容器非空。写入的存储介质存在。

### 2. 放开建行门槛

`0x48D564` 内部的建行判定：

```
0x48D57E  cmp dword [ebx+0x21C], 0x200
0x48D588  jle 0x48D58E        ← 不满足就不建行
```

把它改成 `90 90`（v9），再测 `0x513AAA`：

```
AV=0  GATE8=1  v8=0  rowW=32
```

**格子依旧是 nil。**

### 3. 一个值得注意的规律

v2 / v6 / v9 三次运行里，`0x48D628` 的调用总数恒为 **97**（col0:33 / col1:32 / col2:32）。
我们所做的全部补丁（增长标志、建行门槛、门修复）**都没有改变写入次数**，
说明这些补丁影响的都不是“写不进去”的直接原因。

### 当前唯一确凿的阻塞

```
cm 的第一次网格读（0x513A9C，行 = [0x52315C] = 32，列 2）返回 nil
→ 0x513AAA 跳到收尾，cm 一次都不写第 3 列
```

要越过它，只有两条路（都不在导入流程内插代码）：

1. **改 `0x513A30` 函数体本身**：把 0x513A70/0x513A7D 的门槛与 0x513A9C 的网格读
   换成别处取数（例如直接用 `[0x5230B4]` 数组），这是“替换实现”而非注入；
2. **外部补算**：程序起来后由定时器/线程在导入完成后写列 3。

### 结论

- 无狗版本的 Offset 列（列 2）参数正确、AV=0，这部分工作成立；
- cm 列（列 3）卡在 cm 内部那一次 nil 读，且无法通过外部调用绕过（三次尝试均失败）；
- 下一步必须动 `0x513A30` 本体，属于函数级重写，需要谨慎做。

**结论**：当前会话没有可交互的桌面（无窗口站句柄），

## 九、round 4：决定性判定——所有格子都读不出来

把 cm 首读的行号从 `[0x52315C]` 改成固定 **29**（该行确实有 −5）：

```
0x513A8F  movzx ecx, word [0x52315c]     →  改为  mov ecx,29
```

结果（v10）：

```
GATE8 v8=0  rowW=32      命中 1 次
```

**v8 仍然是 0。** 行 29（有 −5）读回来也是 nil。

### 结论

不是"第 32 行为空"，而是**网格里根本没存进任何数据**：

- 容器 `[grid+0x2D8]` 非空（round 2 已证）；
- setter 被调用 32 次、参数正确；
- 但 getter 对所有行都返回 nil。

即 `0x48D564` 的"创建行 + 插入"路径从未真正执行，
`0x48C768` 查的是一个空列表。我们放开的 `0x48D588` 门槛并不是实际走的那条分支。

### 这解释了整条链

| 现象 | 解释 |
|---|---|
| cm 首次读 nil → 直接退出 | 网格为空 |
| 写入后 cm 不再被有效调用 | cm 只在收尾处理器里跑，且一读就退 |
| 所有补丁都不改变 97 次写入计数 | 那些补丁都没触及真正的插入路径 |

### 阻塞判定

同一个具体条件（**网格单元格不可读 → cm 无法计算 → 第 3 列永远写不出**）
已连续出现在 round 1、2、3、4，符合"连续三轮以上"的阻塞标准。
