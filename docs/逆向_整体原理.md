# PSDTO3D 整体原理逆向

> 建立时间：2026-11-17
> 目的：把三版本（99 / 10.1 / 2022）的实现原理完整还原成可验证的模型，
> 后续任何补丁都必须能在这份模型上推导出来，禁止"猜参数"。
>
> **证据等级约定**
>
> | 等级 | 含义 |
> |---|---|
> | **A** | 二进制约束 + 运行时实测双重确认 |
> | **B** | 二进制/反汇编直接可见（静态强证据），未做运行时交叉验证 |
> | **C** | 由 A/B 推导，数值自洽（有算式或常量吻合），但缺少直接观测 |
> | **D** | 假设，尚未验证；**不得据此打补丁** |

## 2. 启动与授权层

### 2.1 授权闸门（exe）— 等级 A

```
0050300f  call 0x4d2adc            ; 查询加密狗：0=已授权，0xFFFFFBE3=未找到
00503014  cmp  eax,0xfffffbe3
00503019  jne  0x50302a            ; ← 补丁1：75 0F → EB 0F
0050301b  ... ShowMessage("The system did not find any software key...")
00503025  call 0x404ddc            ; Halt
0050302a  call 0x4d2adc
0050302f  test eax,eax             ; ← 补丁2：85 C0 → 31 C0
00503031  je   0x5030ce            ; 已授权 → 正常启动
```

* 2022：文件偏移 `0x102419` / `0x10242F`
* 10.1：文件偏移 `0x10242E` / `0x102444`

`0x4d2adc` 全程序只有 3 个调用点，全在这段启动代码内 → 授权只在启动判一次。

## 3. 工程文件层

### 3.1 两种格式 — 等级 A

两版本同一套文本格式（GBK，CRLF），第 3 行魔数区分：

| 格式 | 魔数 | 第 3 行示例 | 层数位置 |
|---|---|---|---|
| `.tw3d2`（10.1/2022 自家） | `99100` | `99100 50 1575 1890` | 第 3 行第 2 字段 |
| `.gxwj`（99 原生） | `39550` | `39550 0 0 0` | 后文单独一行 |

`.gxwj` 头部少一条横幅、多一个浮点行；曲线块坐标行结尾为 `\r\r\n`。

**2022 解析器原生支持两种魔数**（等级 B）：

* `99100` 分支：`0x511D93` 附近（`cmp edi,0x1831c`）
* `39550` 分支：`0x511D9D` 起（`cmp edi,0x9a7e`）
* 99 旧格式判定：`cmp [ebp-0x20], 0x9984`（0x9984=39300）

### 3.2 工程解析函数

| 版本 | 装载器 |
|---|---|
| 2022 | `0x511408`（约 3.9KB） |
| 10.1 | `0x511790`（精确 +0x37B 同构） |

调用链（等级 A，栈回溯实测）：

```
user32 消息分发
  → exe+0x512931   打开工程命令处理
  → exe+0x511408   装载器
      → 0x403484   ReadLn 跳行
      → 0x403334   读整数 token（Val → int）
      → 0x403484   读浮点 token（Val → float）
      → 0x4029b8   InOutRes 检查（InOutRes<>0 则 raise EInOutError）
```

**已知缺陷（已修）——等级 A**

块循环次数取自布局辅助函数 `0x4D2F14` 的计算值而非层数 → 与文件实际行数不符 →
曲线解析器错位，把图层行的 `1.00000000000000E+0000` 当整数读 → InOutRes=106
→ 抛 `Invalid numeric input` → 后续每个 IOResult 检查连锁弹框。

修复：两处 3 字节等长替换，循环计数改用层数 `[ebp-0x54]`：

* 2022：`0x511A03`、`0x511A81`
* 10.1：`0x511D7E`、`0x511DFC`

### 3.4 组表与空指针缺陷（已修）— 等级 A

`0x509E44` 建两张表，**分三阶段**：外层 SetLength（槽全 nil）→ 填槽 → 建交错表。
50 层/43MB PSD 加载中若发生重绘，会在"槽还全是 nil"时跑渲染校验：

```
movsx edx,ax                 ; 分组号
mov  ecx,[0x52309C]          ; tableA
mov  edx,[ecx+edx*4-4]       ; tableA[group-1]  ← nil
mov  ecx,[0x523158]
mov  edx,[edx+ecx*4]         ; ← AV
```

同型校验共 **6 份拷贝**，2022 全部地址（等级 A，模式扫描）：

`0x4FF960`、`0x500042`、`0x50074A`、`0x5019EE`、`0x5023B4`、`0x501080`

修复：六处 34 字节块改写为"表/组/槽/索引任一无效即按命中处理"的洞穴守卫。

### 4.2 渲染几何

`0x509E44` 建表后用两层循环生成视图：

* 外层 `ebx` = 组序号（0..max-1）
* 内层 `esi` = 视图序号（0..Angles-1）
* 每个 (组,视图) 由 `Round(...)` 计算出交错索引 `edi`，写入 `tableA[组][视图]`

## 5. 导出层（核心）

### 5.1 exe → DLL 调用约定 — 等级 A

`mergtotiff` 通过 IAT 尾跳转调用（`jmp dword [0x524A74]`，包装 `0x4FF1E4`）。

**实参压栈顺序（时间序）**，共 13 个实参 / 64 字节：

```
push al=[0x5230CD]          ① 字节
push al=[0x5230CB]          ② 字节
push ax=[0x52315E]          ③ 字
push    [0x5230E4]          ④
push    esi+0x394           ⑤ 对象指针
push al=[0x523068]          ⑥ 字节（颜色模式）
push    [ebp-4]             ⑦
push al=[0x523069]          ⑧ 字节（通道/份数）
push qword F1 = Round([0x52307C]/25400×10000)   ⑨
push qword F2 = Round([0x523074]/25400×10000)   ⑩
push qword   = [0x523170]                       ⑪ 8 字节
push qword   = [0x52306C]                       ⑫ 8 字节
push    [esi+0x510]                             ⑬ 最后压入 → [ebp+8]
```

**运行时实测（等级 A，1114 工程 + 预览后）**：

| 形参 | 值 | 解读（等级 C） |
|---|---|---|
| `[ebp+8]` | `0x02761160` | 对象指针 |
| `[ebp+0xC]` | **3 120 000** | Angles(13) × LPI(24) × 10000 |
| `[ebp+0x14]` | **240 000** | LPI(24) × 10000 |
| `[ebp+0x1C]` | **39 370** | 纸张高 10 cm → 1e-4 英寸（÷25400×10000） |
| `[ebp+0x24]` | **47 246** | 纸张宽 12.0005 cm → 1e-4 英寸 |
| `[ebp+0x2C]` (byte) | **1** | 通道/份数（dword 高位为垃圾，只用低字节） |

> `0x52306C = Angles × 0x523170` 由 exe 在导出前算出（等级 B，`0x506000` 处
> `fild [ebp-0x10]; fild [0x523170]; fmulp; fistp [0x52306C]`，而 `[ebp-0x10]=13`）。
> 这解释了"开工程后读到 1e8、导出时读到 3.12e6"的差异 —— 该全局被复用。

### 5.4 两条公式（2022 版）

**A. 配置块（0x47F9BF..0x47FA28，105 字节）**

```
[-0x50]  = int64( [-0x1A8] × 10000 )        ; 死
[-0x100] = Round( [-0x1B0] )                ; 死
[-0x104] = Trunc( [-0x1B8] / byte[+0x2C] )
[-0x108] = Round([-0x1B0]) × byte[0x5230... ] ; 死
[-0x10C] = [-0x104]                          ; ← 唯一存活
```

**B. 本地几何块（0x47FA29 起）**

```
[-0x110] = Round( Round( [+0x1C] × [+0x14] / 1e8 ) × ( [+0xC] / [+0x14] ) + 8602 )
```

验算（等级 A，代入实测值）：

```
[+0x1C] × [+0x14] = 39370 × 240000      = 9,448,800,000
/1e8                                     = 94.488 → Round = 94
[+0xC] / [+0x14]  = 3120000 / 240000     = 13
94 × 13                                  = 1222      ← 与实测 [-0x110]=1222 完全吻合
+ 8602                                   = 9824
```

> 实测旁证：早期 FPU 异常现场 dump 到 `[-0x110] = 1222`（等级 A），
> 与上式中间值逐位吻合，证明参数含义解读正确。

### 5.5 99 版对应公式 — 等级 A

99 的 `mergtotiff`（`0x462EF8`）**没有配置块**，直接：

```
[-0xF8] = Round( ( [+0x24] × [+0xC] ) / byte[+0x2C] / 1e8 )
```

`[-0xF8]` 在 99 里被后续 9 处读取（与 2022 的 `[-0x10C]` 角色一一对应，
两处上下文均为 `fild A; fild 该值; fdivp` 的除法结构）。

代入同一组实测值：

```
47246 × 3120000 = 147,407,520,000
/1  = 147,407,520,000
/1e8 = 1474.0752 → Round = 1474
```

`[-0x10C]` 与 `[-0x110]`（1474 vs 9824）同量级，互相印证（等级 C）。

### 5.6 通道缓冲区分配链 —— 等级 A（关键）

`mergtotiff` 后半段（RVA `0x82000` 附近）为**每个"视图通道"分配一块像素缓冲**：

```
0x82004  xor eax,eax
0x82006  mov al, byte [ebp-0x133]        ; 通道/视图数（来自对象虚方法，见下）
0x8200C  push eax                        ; → 动态数组长度
0x8200D  lea eax,[ebp-0x10]              ; 动态数组变量
0x82010  mov ecx,1
0x82015  mov edx,[0x47F4E0]              ; 类型信息
0x8201B  call 0x40521C                   ; @DynArraySetLength(arr, typeinfo, dim=1, len)
0x82023  xor eax,eax
0x82025  mov al, byte [ebp-0x133]
0x8202B  dec eax / jl 跳过               ; 循环 count = [-0x133]
  循环体：
0x82046  mov eax,[ebp-0x124]             ; 行宽
0x8204C  shl eax,2                       ; ×4（每像素 4 字节）
0x8204F  imul dword [ebp-0xFC]           ; × 行数
0x82055  call 0x4026D4                   ; → GetMem(size)
0x8205D  mov [channels+ebx*4], eax       ; 每通道缓冲
```

**像素合成时**（`0x821ED` 附近）：

```
mov dl, al                          ; al = 当前通道号
mov ecx, [ebp-0x10]                 ; 通道数组
mov edx, [ecx + edx*4]              ; channels[ch]   ← 可能为 nil
mov ecx, [ebp-0xF8]                 ; 步长
imul ecx, [ebp-0x124]
add ecx, esi
mov dl, [edx + ecx*4]               ; 取像素 ← AV 现场
sub dl, [ebp+0x44] - 1              ; ↓ 这四步是 CMYK 墨量换算
add dl, [ebp+0x48]
```

### 5.7 三个关键量的来源 —— 等级 A（运行时实测 + 静态确认）

| 局部 | 来源 | 实测值 |
|---|---|---|
| `[-0x133]` | 对象虚方法 `call [obj_vtbl+0xC8]`（`0x7F7AC`），**非配置** | 13 |
| `[-0xFC]` | 硬编码 `mov [ebp-0xFC],0x100`（`0x7FE2C`） | 256 |
| `[-0x124]` | 对 13 个"尺寸对"取**最小值**，初值 `0x493E0`(300000)。尺寸对由虚方法 `call [obj+0x218]+0xC` 逐条取出并写入 `[-0x1F4]` 数组（`0x7FAFA..0x7FB23`） | **0** ← 致命 |
| `[-0x128]` | 同上（另一维），初值 300000 | 1575 |
| `[-0xF8]` | 多处赋值（`0x8013A/0x804C3/0x80D67/0x81C5F/0x820DC`） | 0 |
| `[-0x110]` | 本地公式（§5.4-B） | 1222 |
| `[-0x10C]` | **配置块输出**（或本次补丁计算） | 1474 |

> **实测铁证（等级 A）**：修复公式后，`[-0x10C]=1474`、`[-0x110]=1222` 均为正确非零值，
> 浮点异常彻底消失；但 `[-0x124]=0` 使每个通道 `GetMem(0×4×256=0)` 返回 **nil**，
> 13 个数组元素全为 0，合成循环第一次取像素即 `Read of address 00000000`。

### 5.8 结论（等级 A）

> 导出几何参数**本来就来自 PSD/工程文件与界面设置**（`[+0xC] ~ [+0x24]`）。
> 加密配置缺失导致的后果是**一串**（不是一处）：
>
> 1. `[-0x1A8/-0x1B0/-0x1B8]` = 0 → `fdivr` 除零 → `Invalid floating point operation`（已可绕过）
> 2. `[-0x1F4]` 尺寸对 = 0 → `[-0x124] = 0` → 通道缓冲分配 0 字节 → **nil → AV**
> 3. `[-0xF8]` 步长 = 0 → 即使缓冲非 nil，像素索引也会全部落在第 0 行
>
> **因此"逐个补值"是一条很长的链，不是一次补丁能收口的。**

### 6.2 密码分析结论 — 等级 A（已排除）

| 假设 | 结论 |
|---|---|
| 单字节 XOR | ✘ 256 键穷举最高分 = 随机水平 |
| 位置 XOR（i+1） | ✘ 同 |
| `.enc` 与 `.enc.lll` 为同一明文不同密钥 | ✘ 二者异或无结构 |
| 已知明文 crib（10.1 明文 ini 格式 `15 空格 + 值`） | ✘ 导出的密钥流无重复结构 |

→ 非简单流密码，需真正的算法逆向（`0x72D68` 及 SDK）或硬件样本。

### 6.3 SDK 层 — 等级 B

`cmyktiff2.dll` 内 `0x4620A8 … 0x462130` 是 **20+ 个一跳转发桩**：

```
jmp dword ptr [0x4907FC + n*4]
```

这些槽位在文件中保存的是**提示 RVA**（0x92434… 形如未重定位值），运行期由
`GetProcAddress`/装载器填充；对应外部模块为 `ok3d4.dll`、`rip3d.dll`、
`my32.dll`（USBKey SDK）、`hid.dll`。

### 6.4 狗门禁 — 等级 A

```
全局 hasDog = dword [0x488124]
  · 写 1：0x466BA8（狗初始化成功后）
  · 写 0：0x4676E2（清理）
  · 39 处门禁，形如  cmp dword [0x488124],0 / je skip
运行期实测：hasDog = 0，狗句柄 [0x48DEBC] = 0
```

狗初始化函数 `0x466A5C` 流程：

```
cmp [0x488124],0 ; jne 已初始化→返回
0x4620A8 (SDK)   → 建句柄
0x4620B0 (SDK)   → 打开设备，失败返回 0xFFFFFBB7
0x4620C8 (SDK)   → 取设备信息
0x4621B4 (SDK)   → 构造
0x4620D0 (SDK)   → 传输，失败返回 0xFFFFFBBB
0x466BBC         → 后处理
mov [0x488124],1
```

**已实测：把该函数替换为"直接置 hasDog=1 并返回 0"的桩，导出仍失败**
（等级 A）→ 证明门禁只是开关，配置数据的缺失才是致命项。

### 6.5 导出参数打包器 `0x4626B4` — 等级 B

```
入参：eax/edx/ecx = 三个变量的地址；栈上 20 个槽位地址
流程：
  1. 对 8 个槽位做 StrLen ≤ 0x32(50) 校验（不合法 → 返回 0xFFFFFFDC）
  2. 把 8 个槽位的值转成字符串（0x404334 = StrLCopy）
  3. 读配置文件名 'rip3d.enc.lll'（0x462970）
  4. 调 0x72D68（SDK 解密/校验），参数含狗缓冲区 0x48DBE4、长度 0x4E20(20000)
  5. 返回值 ∈ {0, -0x2B, -0x43} → 视为成功，把解出的 20 个值写回槽位
     否则 → 直接返回错误，**槽位保持调用前的值**
```

> 关键性质（等级 A，代码可见）：**失败时槽位不被写入**。
> 所以调用前设好的默认值（`6, 5, 0x4B0, 0xE6, 0x23, 7`）会保留下来。

### 6.6 解密核心 `0x72D68` — 等级 D（未解）

已知：接收 20 个槽位指针 + 狗缓冲区；成功时校验 4 个值均等于 `0x7B`；
内部无可见的逐字节 XOR 循环（全 DLL 428 个 `xor` 点位筛查后无匹配），
推测为查表/多轮置换或调用外部 SDK。

### 6.7 "设置文件"的真实身份 — 等级 A（实测）

99 版菜单有 `Open settings file`(cmd 10) / `Save settings file`(cmd 11)。
实测触发 `Save settings file`，得到一个 **固定 256 字节**的文件，内容为：

```
偏移 0x00  C:\...\1114-1_便携.gxwj          ← 第 1 行（工程/PSD 路径）
偏移 0x38  " 2.40000000000000E+0001 13 0  1.00000000000000E+0000"
偏移 0x6E  "39550 0 0 0"
偏移 0x7B  "psdto3d99     Email:psdto3d99     "
偏移 0xA0  "Guo Hongmin Tel:psdto3d99&RGB"
偏移 0xBE  " 4.63430000000000E+0004"
偏移 0xD4  " 1.00000000000000E+0004  1.00000000000000E+0000 ..."
```

即：**"设置文件" = 工程文件头部的 256 字节固定块**（不是独立格式）。
2022 的 `导入设置`(cmd 10) 与 `Import default settings` 应读取同类数据。

> 实测保存时同时弹出 `'' is not a valid integer value.` 与
> `Invalid floating point operation.` —— 说明**保存时部分字段为空/为零**，
> 与"UI 输出参数未填"一致。

**推论（等级 C）**：`导入设置` 可能把工程头参数灌回全局变量，间接影响导出几何；
**但尚未证实它能填上 `[-0x1F4]` 尺寸对**。

## 9. 修复策略（按证据强度排序）

### ⚠ 补丁铁律：注入代码绝不能含未重定位的绝对地址（等级 A，踩坑总结）

DLL 的 ImageBase 是 `0x400000`，但运行时被装载到 `0xD30000` 一类地址。
PE 的重定位表只覆盖**原有**重定位项；**新写入洞穴的代码不会获得重定位**。

因此以下写法在洞穴里是**错误**的：

```asm
fdiv  dword ptr [0x4832CC]     ; ✘ 运行时仍访问 0x4832CC（未重定位）→ 读到垃圾/0
mov   dword ptr [0x48FA00],eax ; ✘ 写到未映射地址 → 立即 AV
mov   byte  ptr [0x488124],1   ; ✘ hasDog 永远不会被置 1
```

正确写法只允许：

* `[ebp ± disp]` 栈相对
* 立即数（`mov eax,100000000`）
* 相对跳转/调用（`e9/e8` 用 rel32）
* 若必须访问全局：在洞穴里先按 `ImageBase` 差值算出实际地址再间接访问，
  或改用 `push imm32 / fild [esp]` 这类不落地到绝对地址的写法。

**这条铁律解释了此前全部"补丁无效/AV/行为不一致"的现象**，
包括"强制 hasDog=1 却毫无效果"。

### 路线 A：按 99 公式本地计算 `[-0x10C]`（等级 A，已验证有效）

在 `0x47F9BF..0x47FA28` 处替换为（重定位安全写法）：

```
fild qword [ebp+0x24]
fild qword [ebp+0xc]
fmulp st(1)
movzx eax, byte [ebp+0x2c]
mov [ebp-0x2a8], eax
fild dword [ebp-0x2a8]
fdivp st(1)
mov eax, 100000000          ; 立即数，无重定位问题
push eax
fild dword [esp]
add esp, 4
fdivp st(1)
call 0x402AE4               ; Round（相对调用）
mov [ebp-0x104], eax
mov [ebp-0x10c], eax
```

**实测结果（等级 A）**：
* 浮点异常**彻底消失**
* `[-0x10C] = 1474`、`[-0x110] = 1222`，与手算完全一致
* 但暴露出下一层缺陷：`[-0x124]=0 → 通道缓冲 nil → AV`

**结论：这一步是必要但不充分的。**

### 路线 A+：继续补齐 `[-0x124]` / `[-0xF8]`（等级 C，代价高）

`[-0x124]` 来自 13 个"尺寸对"，这些尺寸对由 `call [obj+0x218]+0xC` 提供。
若该虚方法的返回值本身依赖配置（打印版面），则必须逐层还原 —— 风险是链条很长。

### 路线 B：绕过 `cmyktiff2`，自建 TIFF 输出（等级 C，工作量可控）

渲染层产物已完全可用（`vw1..vw13.bmp`，1200×1440，32bpp）。
可以：

1. 只借用 `bmptotiff`（若它不依赖配置）；
2. 或直接用 13 张视图位图按目标版式自行拼合写出 TIFF（标准库即可）。

优点：**彻底脱离配置/狗**；缺点：需要确定目标版式（拼合规则）。

### 路线 C：从有狗机器抓解密后的配置（等级 A，最快）

有狗机器上导出成功后，配置值即为可用明文。抓取点明确：

* `0x626B4` 返回后，20 个槽位（`[-0x168]..[-0x1E0]`）
* 以及 `[-0x1F4]` 尺寸对数组

### 路线 D：借用 99 模块（等级 A，已验证部分可行）

* 换 `cmyktiffd.dll` → 除零**彻底消失**
* 补 `ok3d4d.dll` → `EFOpenError` 消失
* 卡在 `EInvalidGraphic`（99 期待的中间图像格式与 2022 产物不同）

## 11. 观测手段备忘（踩过的坑）

| 手段 | 结果 |
|---|---|
| **注入代码使用绝对地址** | ✘✘✘ **不重定位，全部失效**（本项目的最大坑，见 §9 铁律） |
| 调试器 + INT3 于 DLL 函数入口 | △ 可命中，但会改写 FPU 控制字（Delphi 0x1332 未掩码模式），导致浮点行为失真；**抓 AV 可用** |
| 调试器读 `CONTEXT.FloatSave` | ✘ WOW64 下全 0，不可用 |
| 内存打点到 CODE 扩展区 | ✘ 该页只读 → 写入 AV |
| 内存打点到 DATA 尾部 | ✘ 越界未映射 → 写入 AV |
| 内存打点到 BSS | ✘ 同样因**未重定位**而写到 0x48xxxx 未映射区 |
| 无调试器 + 读进程全局 | ✔ 可靠（参数、常量、状态） |
| 调试器抓 `0xC0000005` + `owning()` + EBP 链 + 读 `[ebp±x]` | ✔✔ **最有效**（精确定位故障指令与局部值） |
| 静态模式扫描（字节签名 / 逐指令写读分析） | ✔✔ 最可靠，本文档主要依据 |

**方法论结论**
1. 先静态建立模型，再运行时验证数值；
2. 运行时只读不写（除受控的补丁测试）；
3. Delphi AV 消息里的地址是**绝对地址**，必须先减模块基址才是 RVA；
4. 任何洞穴补丁必须通过"重定位安全"审查。
