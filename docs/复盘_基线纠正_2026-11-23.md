# 复盘：基线跑偏与纠正（2026-11-23）

> 结论先行：**去狗任务的正确基线是 `psdto3d2022绿色版/`**。
> 我此前大部分工作跑在 `Psdto3d/`（2025-03-24 的另一个构建）上，属于跑偏。
> 但两个构建的二进制**几乎完全相同**，所以大部分技术结论仍然成立，只有"交付包"和"头部格式"两件事必须重做。

## 一、两个构建的客观差异（实测）

| 项 | `Psdto3d/`（我误用的） | `psdto3d2022绿色版/`（正确基线） |
|---|---|---|
| `psdto3d101.exe` | 1,581,056 B，2025-03-24 | **1,584,140 B，2026-11-17** |
| `cmyktiff2.dll` | 628,736 B，2025-04-07，md5 `417ce3b6…` | 628,736 B，2025-04-07 时间戳但内容不同，md5 `2134e30b…` |
| 基准 TIFF | — | `…第一人称海报汉化.tif`，6,899,708 B，**2026-11-17 15:44** |

### exe 差异

| 段 | 结果 |
|---|---|
| CODE | 1,127,424 → 1,130,496 B（多 3,072 B 尾部代码）；重叠部分仅 **435 字节**不同 |
| DATA / .idata / .reloc / .rdata | **完全相同** |
| .rsrc | 57,384 字节不同（资源：字符串/对话框），文件体积差来自这里 |
| **补丁点字节** | `0x4D2BF2`、`0x504C72`、`0x4D2ADC` **逐字节一致** |
| 菜单/函数偏移 | 六个探针（`0x50B070/7E/86`、`0x505A66`、`0x43265E`、`0x50B073`）字节全部匹配 |

⇒ **所有针对 exe 的分析与补丁都继续有效**，不需要重做。

### DLL 差异（关键）

CODE 段 534,016 字节里**只差 6 个字节**，全部是 `savetiff00` 里的"十进制字符串常量"：

| 用途 | 10.1 套件写的 | 2022 写的 | 十进制含义 |
|---|---|---|---|
| 文件头 magic | `"18261"` = 0x4755 | `"18761"` = 0x4949 | `"UG"` vs **`"II"`** |
| 第二 dword | `"423"` = 0x1A7 | `"42"` = 0x2A | **TIFF 魔数 `*`** |
| IFD 偏移 | `"1"` | `"8"` | 标准 TIFF 头长 |
| 标签 1 | `"259"` = Compression | `"256"` = **ImageWidth** | |
| 标签 2 | `"274"` = Orientation | `"273"` = **StripOffsets** | |

**这就是我们输出 `55 47 A7 01…`、基准却是 `49 49 2A 00 08 00 00 00…` 的全部原因**——
不是"渲染差异"，是这两个构建**字面上的 6 个字符串常量不同**。

⇒ 用 2022 的 `cmyktiff2.dll` 作 `cmyktiff2_real.dll`，头部立刻变标准 TIFF。

## 二、跑偏的范围与影响

| 已做的工作 | 是否受影响 |
|---|---|
| 狗协议逆向（SPT/A5、slot 0x01F0/0x001A/0x00C2/0x0012） | ✅ 不受影响（协议在 exe/dll 两侧都没变） |
| 63 事件回放表、emu 仿真器 | ✅ 不受影响 |
| IAT 按 API 地址挂钩（不绑版本） | ✅ 不受影响，且正好支持 2022 版 |
| 许可证记录语义（X1/X2 来自狗记录字段） | ✅ 不受影响（DLL 只差 6 字节常量） |
| `stai` 才是真正合并核心 | ✅ 不受影响 |
| **交付包 `_work/完整程序/`** | ❌ **必须重做**（用的是 10.1 exe + 10.1 DLL） |
| "头部差异属版本渲染差异"的判断 | ⚠️ 方向对但没查到底——**我们手上就有正确版本** |
| 像素内容差异（mean abs diff ≈ 50） | ❓ 未解释，需在新基线上重跑再判 |

## 三、我犯的具体错误

1. 开工时取 `Psdto3d/` 目录（第一个含 `psdto3d101.exe` 的目录），没有核对"2022 版才是基准"。
2. 生成"完整程序"时，直接把 `_work/emu1`（基于 10.1）的产品打包交付。
3. 看到头部 `UG` vs `TIFF` 差异时，直接归因为"版本差异"，没去 diff 两个 `cmyktiff2.dll`
   —— 而那 6 个字节就摆在那里。

---

## 四、纠正后的执行顺序

1. **重建基线包**：以 `psdto3d2022绿色版/` 为源，`cmyktiff2.dll` 换成仿真器，
   原 DLL 改名 `cmyktiff2_real.dll`；exe 打同样两处补丁（字节已验证一致）。
2. **跑通全流程**：导入 → 设置 → 预览 → 导出，比对基准 TIFF：
   - 头部应为 `49 49 2A 00 08 00 00 00`，标签 `0x00FE/0x0100/0x0101/0x0111`
   - 尺寸 1969×1168，像素区 6,899,376 B
3. **若像素仍有差异**：在新基线上逐段对比（预览中间文件 → 分色 TIFF → stai 输出），
   不要再拿 10.1 的产物做参照。

## 五、教训（写给自己）

- **先确认基准，再动手**。目录里有多个构建时，第一件事是核对"哪个是任务基准"，
  并把它写进文档抬头的"当前版本"一节。
- **差异要 diff 到底**。见到"格式不同"不要用"版本差异"打发，binary diff 往往直接给出答案。
- 交付前自检：交付包里的每个二进制，是否都来自被确认的基线。
