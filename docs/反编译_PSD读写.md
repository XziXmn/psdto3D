## 0. 为什么是 `zu06.dll` 而不是 `8602.dll`

2022 主程序**不引用** `8602.dll`（全语料零命中），它实际 `LoadLibrary("zu06.dll")`
并取 `readpsd` / `writepsd`（详见 `docs/反编译_8602.md` 第 4 节）。
本文以 `zu06.dll` 为准，`8602.dll` 作为同族变体在末尾对照。

| 项 | `zu06.dll` | `8602.dll` |
|---|---|---|
| `readpsd` | `0x4A2A58`，844 行 | `0x4B9528`，701 行 |
| `writepsd` | `0x4A4504`，658 行 | `0x4BAA64`，585 行 |
| 业务单元 | 32 | 53 |

## 2. `readpsd`（`0x4A2A58`，844 行）

### 2.1 开头：一个实际可用的缩放规则（B 级，本模块最有价值的发现）

```c
local_7c = FUN_004165d0(&PTR_LAB_004127dc, 1, filename, 0);   // 打开流
vtable+0x14(stream, 0xe, 0);                                  // Seek(14)
FUN_00416348(stream, &v, 4);  *out_w = bswap(v);              // 行 219-221
FUN_00416348(stream, &v, 4);  *out_h = bswap(v);              // 行 222-224

if (*out_h < 0x5DD) {              // 0x5DD = 1501
    *out_scale = 10000;            // 1.0（以 1/10000 为单位）
    *(out_scale + 4) = 0;
    *out_h2 = *out_h;
    *out_w2 = *out_w;
} else {
    *out_scale = ROUND((1200.0 / *out_h) * 10000.0);   // 行 233
    *out_h2 = 0x4B0;                                   // 1200
    *out_w2 = FUN_004029e8();                          // 按比例算出的宽
}
```

**规则**：图片高度 ≤ 1500 像素时原样使用（缩放系数 10000，即 1.0）；
超过 1500 时，等比缩放到高度 1200，缩放系数以 1/10000 为单位保存。

这条对重写直接可用：它解释了程序内部所有坐标/尺寸为什么以万分比表示。

> **归属已核对（第 50 轮）**：这条规则确实在 `zu06!readpsd`（`0x4A2A58`）体内——
> 语料里对应 `_analysis/dump_zu06_b/004a2a58.c` 的 **L231**（`if ((int)*in_stack_0000000c < 0x5dd)`）
> 与 **L240**（`*in_stack_00000014 = 0x4b0;`）。**A 级**。
>
> 旁注：`cmyktiff2!mergtotiff` 里**没有** 1500/1200 这对阈值（只有一处 `local_170 = 0x4b0`
> 是组装调用参数的常量，与缩放无关）。不要把这套规则套到 mergtotiff 上。

### 2.2 随后：按 PSD 结构往下走（B 级）

```
行 239  vtable+0x14(stream, 2, …)                     // Seek(2)
行 240  读 2 字节，手工交换高低字节                     // 通道数（大端 16 位）
行 242  读 4 → bswap → Seek(该值)                      // 跳过「颜色模式数据」段
行 245  读 4 → bswap → Seek(该值)                      // 跳过「图像资源」段
行 252  读 4；行 253 读 4；行 254 读 2                  // 图层段
行 255-262  计算一个有符号值，为 0 时改成 3
```

「读长度 → Seek 跳过」的两段式，正是 PSD 里 `Color Mode Data` 与 `Image Resources`
两节的通行处理方式。

### 3.1 文件头逐字段写出（B 级）

```c

146–147  write 4 字节 bswap(宽度)
```

### 3.2 图层记录（B 级）

- 行 167：`local_110 = (local_28 - 1) * 0x19` —— 每层索引乘以 **25**。
  **⚠️ 这不是文件里的图层记录长度**：真实记录是变长的（矩形 16 + 通道数 2 + 每通道 6 +
  混合模式 8 + 额外数据…），实测首个记录从偏移 44 起、远超 25 字节。
  `0x19` 更像是某个**内存参数数组的步长**，用途未定，**不做结论**；
- 行 171–178：写图层矩形（0, 0, 高, 宽）；
- 行 179–181：写通道数 + 1；
- 行 184–189：每个通道写 `2 字节通道号` + `4 字节 bswap(宽*高 + 2)` ——
  **`+2` 是压缩方式字段的长度**，这是 PSD 通道数据的标准写法；
- 行 191–192：写 4 + 4 字节（混合模式签名与键）；

### 3.5.1 更正：`0x4029E8` 是 Delphi 的 `ROUND`

第 2.1 节里写作：

```c
*out_h2 = 0x4B0;                 // 1200
*out_w2 = FUN_004029e8();        // 按比例算出的宽   ← 错
```

`FUN_004029e8` 实为 **`@ROUND`**（Delphi 取整原语）。正确的读法是：
**表达式先按比例算出宽，再交给 `ROUND` 取整**，而不是「这个函数算宽度」。

数值结论不变（高度 >1500 时按 1200 等比缩放），但代码归属要说对。

### 3.5.2 导出同样是 `stdcall`

```
{zu06} readpsd;  stdcall;      {zu06} writepsd; stdcall;
```

与 `cmyktiff2` 一致——**PSD 读写这两个入口也是 `stdcall`**。

## 3.9 PSD 读写族的符号级关系（第 49 轮，A 级）

对五个成员各做一次 IDR 分析，按「单元 + 函数名」比集合（与布局无关）：

| | zu6 | zu61 | zu06 | 8602 | dspr |
|---|---|---|---|---|---|
| 命名函数 | 2,479 | 2,479 | 2,479 | **3,119** | 2,467 |
| Jaccard（对 zu06） | **1.000** | **1.000** | — | 0.785 | **0.995** |

**结论**：`zu6`、`zu61`、`zu06` 的命名函数清单**完全相同**；`dspr` 几乎相同（0.995）；
`8602` 是唯一的外点（0.785，且函数数多出约 640 个，另带 `TREG` 窗体）。

### 3.9.1 与字节相似度的冲突及解释

早先按「同长度前缀逐字节比对」得到：`dspr` 与同族只有约 3.7% 相似。
两者矛盾，原因是**布局平移**：

| | zu6 vs zu61 | zu6 vs dspr |
|---|---|---|
| 单元名相同 | 66 | 66 |
| 初始化地址也相同 | **66 / 66** | **1 / 66** |
| 整体地址差 | 0 | **≈ −1.8 KB** |

`dspr` 是同一份源码用**不同链接布局**编出来的。固定偏移比对时整体平移会让字节全错，
于是得出 3.7%。**字节法只在「几乎同一构建」时有效。**

本文第 2、3 节对 `zu06` 行为的描述，对 `zu6`/`zu61`/`dspr` **同样适用**——
它们共享同一套函数清单。

### 3.95.1 P6 的正确理解（改口径）

初版把「通道长度 ≠ 行×列+2」当违规，报了 1005 条。实际那是我公式太窄：

| 8 位图层的颜色/透明通道（8,016 个） | 数量 | 占比 |
|---|---:|---:|
| 长度恰为 `行×列+2`（未压缩） | 1,806 | **22.5%** |
| 其他（**RLE 压缩** 或 掩码通道） | 6,210 | **77.5%** |

所以：**约四分之三的通道是 RLE 压缩的**，读侧必须实现 PackBits 解压，
不能假设「长度 = 行×列+2」。这条对重写至关重要。

### 3.95.2 四个异常样本：宽度为 0

## 3.96 RLE 解压到底在哪？——一个问题与两个候选（第 55 轮）

第 3.95 节实测：真实 PSD 里 **77.5% 的通道是 RLE 压缩的**。那么 `readpsd` 必然要解压。

### 3.96.1 `readpsd` 的实际行为（A 级，来自调用统计）

| 被调 | IDR 实名 | 次数 |
|---|---|---:|
| `FUN_00416348` | `TStream.ReadBuffer` | **37** |
| `FUN_004029E8` | `@ROUND` | 15 |
| `FUN_004A2654` | `sub_004A2654`（字节序翻转） | 12 |
| `FUN_00422238` | `TBitmap.GetCanvas` | 12 |
| `FUN_004231E8` | `TBitmap.SetPixelFormat` | 10 |
| `FUN_00421C70` | `TBitmap.Create` | 6 |
| `FUN_0041611C` | `TStream.GetPosition` | 5 |

**`SetPosition` 出现 0 次、`TFileStream.Create` 出现 0 次。**
所以 `readpsd` 是**纯顺序读**：接收一个已打开的流，从头读到尾，边读边建 `TBitmap` 对象。

### 3.96.2 两个 PackBits 解码器，但都没人调用

`zu06` 里有两条完整的 PackBits 实现：

| 函数 | 风格 | 特征 |
|---|---|---|
| `FUN_00485268` | **PSD 风格**（8 位控制字节） | `(*param_2) += 2` 跳过每行字节数；`b & 0x80` 分复制/重复；`b == 0` 行结束 |
| `FUN_004851ac` | **TIFF 风格**（大端 16 位控制字） | `*w & 0x8000`、`>> 8 & 0x7f`；按位深 8/16 分两支 |

在 `zu06` 的**全部 3,850 个函数里，这两个都没有调用者**（`FUN_00485268(` / `FUN_004851ac(` 各 0 处引用）。

### 3.96.3 结论与未决

- **已确认**：`readpsd` 顺序读、建 `TBitmap`、不做 Seek；
- **已确认**：`zu06` 内自带两条 PackBits 实现，但本构建中无直接调用者；
- **未决（C 级）**：RLE 究竟在哪一层解压。可能的位置：
  1. 主程序拿到压缩缓冲后自行解压（`psdto3d101.exe` 里有 5 个 PackBits 特征函数）；
  2. 通过 `TBitmap.LoadFromStream` 之类的 VCL 路径；
  3. 这两个函数由运行时构造的函数指针调用（Ghidra 看不到直接引用）。
- **不建议**：在没有进一步证据前断言「`readpsd` 自己解压」。

> 重写视角：**解析器必须实现 PSD 风格的 PackBits**（每行先 2 字节长度、控制字节高位分复制/重复），
> 这一点由真实文件和 `FUN_00485268` 的实现共同支持，不受上面归属未决的影响。
