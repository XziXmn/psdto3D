## 二、关键发现（都写进工作单了）

1. **导出菜单是阶梯解锁**：预览后只开 `Export tiff`；成功导一次 TIFF 后 `Export PSD` / `Export Gif` 才可用。
2. **GIF 有自己的闸门**：`N18Click@0x50B010` 检查 `[form+0x3EC]` 的 `.Down`，不是 Down 就静默返回。
   补丁 `75 09 → 90 90`（**按字节模式定位**，绿色包与 emu1 的 exe 偏移差 0x1E0）。
3. **`writepsd` 的真实签名**（探针实测）：
   `writepsd("C:\bio\out.psd", "c:\ok3dtemp\", 3000000, 0, 252000, 0, 11, 4370, 5197, 3)`
4. **PSD 层的宽/高来自局部量 `[ebp-0x14]/[ebp-0x18]`**：注入 5197/4370 后结构立刻正确。
5. **一个旧结论被推翻**：`cmyktiff2.dll` 里那 6 个"TIFF 常量"**不在实际导出路径上**，
   改它们不会改变产物（`复盘_基线纠正_2026-11-23.md` 的相关推论不成立）。
6. **一个坑**：`C:\ok3dtemp` 不干净会让"导入工程设置"报 `Invalid numeric input` ——
   每次实验前必须清空。

## 三、还没拿下的（只剩下一个）

**A6 导出 PSD 的像素数据。**

现状：层头完全正确（11 层 × 4 通道 × 22.7 MB 都已声明），**但一个像素字节都没写**，文件只有 2,970 B。

**已经定位到根因链（06:2x 更新）**：

1. PSD 的层宽来自 TIFF 的 `ImageWidth` 标签（0x0100）；
2. 我们的 `vwd*.gjs` 是"UG 变体 TIFF"，把宽度写成了 tag **0x0103**，**没有 0x0100**
   → 加载器读到 width = 0 → 层矩形 `(0,0,4370,0)` → 不写通道数据；
3. 对照标准 TIFF 只差 4 处：`文件头 8 字节` + `3 个 tag 号`（已做成工具 `tools/ug2tiff.py`，静态验证通过）；
4. 但**写 `vwd*.gjs` 的模块还没抓到**：`zu06` 的 WriteFile 抓不到，`cmyktiff2_real` 的常量改过也没效果，
   `exe` 里的"常量字面量"经逐字节核对是误报。

**下一步（纯本地，不需要真机）**：给 exe 的 `WriteFile`（`RVA 0x124294/0x124348`）挂日志壳，
按"68 MB 的那次写"确定模块，再在该模块里把文件头改成 `II*\0` + tag 0x00FE/0x0100/0x0111。

**备用路线**：真机插狗跑一次「导出 PSD」，回传 `_dongle.log`，用 A5 回放直接闭环。

已知：
- `writepsd` 会打开 `ly*/lyt*/vwd*/vwdt*`（都在、都可读）；
- 还会打开 `readpsdpwph.enc.lll`（加密的 PSD 参数文件）并做 **768 次** `\\.\MyUSBKey#` 设备探测；
- 无 CryptoAPI，`.enc` / `.enc.lll` 的 XOR 呈 8 字节块重复 → 自研分组密码，密钥与狗绑定；
- 删掉 `.lll` 不会回退到 `.enc`（已试）。
- 最近一次探针：`zu06+0xA497D`（层循环头）零命中，且 `zu06+0xA4800` 只命中一次 ——
  与工作单「禁忌 9」记的断点失效现象一致，后续要换"内存标记/IO 日志"类证据。
